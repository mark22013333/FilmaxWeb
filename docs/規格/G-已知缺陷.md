## G. 現在就已經壞掉的東西

盤點資料層時挖出的既有缺陷，每一個都在資料或程式碼上驗證過。

### G-1 孤兒條目清理只有在「有相片」時才會跑　【高】

```python
if seen_photos and not _cancel.is_set():
    with db.tx() as conn:
        ...刪掉消失的相片...
        conn.execute("DELETE FROM media_item WHERE id NOT IN (...)")   # ← 在這裡面
```

影片與相片是兩件獨立的事卻被綁在一起。**純影片的片庫永遠不會清孤兒條目**；
相片掃描被取消或出錯時也不會清。

### G-2 相片排序是錯的　【高】

`photo.mtime` 存 `2026-07-12T14:30:29`（**T** 分隔），
`photo.taken_at` 存 `2026-03-19 00:29:05`（**空格**分隔），
而排序是 `ORDER BY COALESCE(taken_at, mtime) DESC` — 字串比大小。

`' '`(0x20) < `'T'`(0x54)，第 11 個字元就分勝負，**後面的時間根本沒被比到**：

```
taken_at = '2026-03-19 23:59:59'   ← 晚上快 12 點
mtime    = '2026-03-19T00:00:01'   ← 凌晨 12 點過 1 秒
字串比較：mtime 比較「大」，排在前面
```

**同一天內，只有 mtime 的照片永遠排在有 EXIF 的前面**，不管實際差多久。
資料庫裡排最前面的 8 張全是 mtime 那組。FTP 的 mtime 還有三種其他格式
（`Mar 15 10:22`、`03-15-24 10:22AM`、空字串），`Mar` 開頭的會直接跳到全表最上面。

修法見 A-3。

### G-3 按下「停止掃描」最多還要等 90 秒 × 併發數　【中】

探測函式只在**進入時**檢查一次取消旗標，而 `ffprobe` 的 timeout 是 90 秒。
使用者看到的是「按了沒反應」。修法：旗標傳進去、每個可中斷點檢查、子行程能被終止。

### G-4 98 集的影集會有 98 個工作搶著產生同一張底圖　【中】

`COALESCE` 讓它不會覆蓋既有值，但**兩個工作同時看到「還沒有底圖」時，兩邊都會各跑一次 ffmpeg 截圖**
— 兩次轉碼、兩個磁碟檔，其中一個立刻變成孤兒。
修法：探測階段只記錄候選，全部結束後單執行緒處理一次。

### G-5 縮圖檔名重用可能讓你看到別人的照片　【高】

縮圖檔名是 `ph_{id}.jpg`，而產生函式**看到同名檔已存在就直接回傳，不重畫**。
id **會**被重用：還原備份、切換後端、砍掉 `library.db` 重掃之後，
新的第 7 張仍叫 `ph_7.jpg`，於是顯示**舊的第 7 張**的縮圖。點進去是對的，牆上是錯的。

**這是隱私問題，不是顯示問題。** 決策 4 已確認採徹底修法：檔名改用**內容雜湊**。
既有 679 張縮圖要重新產生一次。

### G-6 編碼器選項解析在 ffmpeg 4.x 上抓到空清單，硬體轉碼的畫質不受 CRF 控制　【高】　**已修**

`media.encoder_option_values()` 用這條 regex 抓 `ffmpeg -h encoder=` 的常數列：

```python
re.match(r"^([A-Za-z0-9_.\-]+)\s+[-]?\d+\s+[EDAVS.]{6,}", stripped)
```

它要求值的後面**必須有一個數字欄**。ffmpeg 5.x 有，**4.x 沒有**：

```
ffmpeg 4.2   →      slow                         E..V..... hq 2 passes
ffmpeg 5.x+  →      p4              15           E..V....... medium (default)
```

而這台機器上跑的是 4.2.3。於是 `pick_option()` 拿到空清單就回 `None`，
`_quality_arg_tiers("h264_nvenc")` 的 preset 與 rc 都變成 `None`，
第一個 tier 從「完整」退成 **「僅 cq」**——

> 實際下給 ffmpeg 的是 `-c:v h264_nvenc -cq 21`，
> **沒有 `-rc vbr`、也沒有 `-b:v 0`**。

而 NVENC 的 `-cq` 只在 VBR 模式下有意義，`-b:v 0` 才是「不要用位元率當目標」。
兩個都缺的時候，實際生效的是編碼器／ffmpeg 的預設位元率 ——
**也就是說走硬體編碼時，`TRANSCODE_CRF` 對畫質沒有作用。**

修法是一行：

```python
# 數值欄改成可有可無
re.match(r"^([A-Za-z0-9_.\-]+)\s+(?:[-]?\d+\s+)?[EDAVS.]{6,}", stripped)
```

`app/vidprobe.py` 已經是修好的版本，可以直接對照。修好之後 `-preset`／`-rc`
會被正確選到（4.2 上是 `hq`／`vbr`，不是 `p4`／`vbr_hq`），
`_quality_arg_tiers` 的「完整」tier 才真的會被用到。

**同一個坑我自己也踩了一次**：量測工具的前一版直接賭 `p4`，
在這台機器上兩組 NVENC 變體都失敗（`Undefined constant or missing '(' in 'p4'`）。
差別是工具會把失敗印出來，而生產環境的失敗會被
「硬體轉碼失敗就退回 CPU」那條路徑吃掉 —— 使用者只覺得變慢。
