## R. 上階分段互相重疊：每隔幾秒畫面往回跳

### R-0 症狀

使用者回報兩個檔案的差別：

* `來！金來號S107.mp4`（file 3269）—— **不會**往回跳。
* `Reacher.S02E07...H.264-NTb.mkv`（file 360）—— 每隔幾秒畫面往回跳。

### R-1 第一個結論：這不是 mp4 與 mkv 的差別

兩個檔案真正的差別是 **keyframe 間距**，而間距決定了「這個檔案會不會發上階（remux）」：

| | 金來號 mp4（3269） | Reacher mkv（360） |
|---|---|---|
| `gap_med` | **10.427 秒** | **2.002 秒** |
| `> HLS_SEGMENT_SECONDS`(6)？ | 是 | 否 |
| `rungs_for()` 給幾階 | **只有下階（轉碼）** | 上階 + 下階 |
| 會不會往回跳 | 不會 | **會** |

`rungs_for()` 把金來號擋在上階之外：

```python
gap = row["gap_med"] or 0
if gap <= 0 or gap > settings.hls_segment_seconds:
    return rungs        # 只發下階
```

**金來號不跳，不是因為它沒毛病，是因為它根本沒走到有毛病的那條路。**
全庫統計證實「mkv 才會壞」是錯的歸因：

```
有 keyframe 表：181 個，其中會發上階（受影響）：172 個
受影響副檔名分布：mkv 107、mp4 46、mov 19
不受影響（不發上階）：mp4 9 個  ← 金來號在這 9 個裡面
```

**有 46 個 mp4 同樣受影響。**真正的判準是 `gap_med <= 6`，不是副檔名。

### R-2 根因：`-ss` 落在 keyframe 上，ffmpeg 仍然退一格，而那一格沒有被丟掉

#### R-2-1 量測

完全照 `build_remux_cmd()` 目前的參數，對 file 360 產生連續三段
（邊界取自 `derive_bounds()`）：

```
seg100 宣告[600.600, 606.606]  video 實際[598.598 .. 606.648]
seg101 宣告[606.606, 612.612]  video 實際[604.604 .. 612.779]
seg102 宣告[612.612, 618.618]  video 實際[610.610 .. 618.743]
```

接縫：

```
seg100 尾 606.648  vs  seg101 頭 604.604   → 重疊 2.044 秒
seg101 尾 612.779  vs  seg102 頭 610.610   → 重疊 2.169 秒
```

**每個接縫都重疊約一個 keyframe 間距（2.002 秒）。**
`gap_med` 越大重疊越久 —— 2 秒的片子就是「每 6 秒往回跳 2 秒」，
正是使用者描述的頻率。

#### R-2-2 邊界確實是真的 keyframe，退格不是因為邊界算錯

一度懷疑 `derive_bounds()` 算出來的邊界沒落在 keyframe 上。**實測否定了這一點**，
`media_keyframe` 存的值與容器完全一致：

```
DB 存的        : 596.596  598.598  600.600  602.602  604.604  606.606
ffprobe 實際封包: 596.596  598.598  600.600  602.602  604.604  606.606  （全部 flags=K__）
```

邊界是貨真價實的 keyframe，ffmpeg **仍然**退一格。
這與 `build_remux_cmd()` docstring 裡已經記載過的行為一致
（「copy 模式下 ffmpeg 一律退到前一個 keyframe 才開始抄」）。

#### R-2-3 `190647b` 只修了標籤，沒有修內容

commit `190647b` 用 `-copyts` 修掉了「多抄的那段被貼上錯的標籤」。那是對的，
但它的結論是：

> 與前一段重疊的區間被**同樣的內容**覆寫，是冪等的，播放頭不動。
> 段與段之間重疊沒關係，**標錯位置才有關係**。

**這個假設不成立，有兩個獨立的理由：**

**（一）音訊不是 copy，所以不冪等。**
`audio_can_copy()` 只在「原本就是 AAC 且聲道數符合 `AUDIO_CHANNELS`」時才回 true。
Reacher 是 **eac3**、金來號是 **6 聲道 aac**（而 `AUDIO_CHANNELS=2`）——
兩個都要重新編碼成 AAC。重編的 AAC 不會產生位元相同的輸出，
frame 邊界也與前一段不對齊。實測目前的參數：

```
seg100  video 頭 598.598   audio 頭 600.578     ← 差 1.98 秒
```

每一段開頭都有一個「有畫面、沒聲音」的洞，而那個洞正好蓋在前一段的聲音上。
往 SourceBuffer append 重疊但**內容不同**的音訊，MSE 的行為是覆寫 ——
前一段最後 2 秒的聲音被後一段的靜音區蓋掉。

**（二）hls.js 會主動修正播放位置。**
重疊讓 `EXTINF` 累加出來的時間軸與 SourceBuffer 的 `buffered` 區間對不上。
hls.js 偵測到 `currentTime` 落在預期分段之外時會 seek 回去對齊 ——
那一次 seek 就是使用者看到的「畫面往回跳」。

這與 `4aa1653`（ABR 切階不對齊）是**同一個表現、不同的成因**，
所以修好 ABR 對齊之後症狀仍在。本章不是它的重複。

#### R-2-4 附帶釐清：mpegts muxer 還會再平移一次

診斷時容易被這一層誤導，記下來避免下次重查：
同一段輸出成 mkv 與 mpegts，落點不一樣。

```
-ss 600.600 輸出 matroska → 第一個封包 pts 598.598   ← demux 真正的落點
-ss 600.600 輸出 mpegts   → 第一個封包 pts 599.998   ← muxer 又平移了約 1.4 秒
```

**demux 的回退（2.002 秒）才是要修的東西**；mpegts 那 1.4 秒是 muxer 的
初始 PCR 行為，兩階一致，不造成階間不對齊。

### R-3 修法

#### R-3-1 主修：會退格的檔案才把 `-ss` 推到「下一個 keyframe」　【高】

回退量本身修不掉（copy 模式需要前一個 IDR 才敢起頭，微調 `-ss` 無效，
docstring 已記載）。**能修的是餵給它什麼起點**：把 `-ss` 往後推一格，
demux 退回來之後剛好落在我們宣告的邊界上。

> **但「一律退一格」是錯的 —— 實作時才發現，記在這裡。**
> 規劃階段在 file 360／297／438 上量到的退格都是一整格，於是以為那是
> copy 模式的普遍性質。**不是。**實測把同一份視訊 `-c copy` 換個容器再測：
>
> ```
> abr.mp4  -ss 3.480 → 落點 3.480   （完全不退）
> abr.mkv  -ss 3.480 → 落點 0.000   （退一整格 3.48 秒）
> ```
>
> 同樣的視訊內容、同樣的 keyframe，**只換容器就換了行為**。
> 全庫 172 個會發上階的檔案裡有 65 個是 mp4／mov —— 對這些檔案無條件推後，
> 那一段的開頭會整個缺一格（實測 seg0 從 0.000 變成 4.880，缺 4.88 秒）。
>
> 而且**也不能用副檔名判斷**：金來號那個 mp4 實測是會退格的（1136.552 →
> 1126.125）。退格取決於容器的 index 結構，推導不出來。
>
> 所以改成**每個檔案量一次**，量出來的值存進 `media_file.seek_backoff`
> （1=會退、0=不退、NULL=還沒量）。`_produce()` 只在 `seek_backoff=1` 時推。
> **猜錯的代價不對稱**：該推沒推只是接縫重疊（原本的 bug），不該推卻推了是
> 那一段開頭整個缺畫面 —— 所以 NULL 一律當作不退。

邊界表本身已經有每一個 keyframe 的時間，所以「下一格是誰」是查表得到的，
**不是算出來的**——不必假設間距均勻。

```python
# spans 來自 bounds_for()；times 來自 keyframes.table_for()
# seek_at = 在 times 裡，start 之後的第一個 keyframe（沒有就用 start 本身）
pre = [resolve_tool("ffmpeg"), "-v", "error", "-nostdin", "-y",
       "-copyts",
       "-noaccurate_seek",            # 見 R-3-2
       "-ss", f"{seek_at:.3f}",       # ← 不是 start
       *input_args(file_id),
       "-to", f"{start + duration:.3f}",
       ...]
```

**實測結果**（file 360，同一組 seg100/101/102）：

```
              修法前                    修法後
seg100 video  [598.598 .. 606.648]     [600.600 .. 606.648]
seg101 video  [604.604 .. 612.779]     [606.606 .. 612.779]
seg102 video  [610.610 .. 618.743]     [612.612 .. 618.743]

接縫重疊       2.044 / 2.169 秒         0.042 / 0.167 秒
```

video 起點與宣告邊界**完全一致**，重疊從 2 秒降到 0.04~0.17 秒。

> 殘餘的 0.04~0.17 秒是 B-frame 造成的 PTS 亂序（尾端最後幾張 B-frame 的 PTS
> 大於宣告的結束時間），**不是回退**。這種重疊是同一批封包的顯示順序問題，
> MSE 可以正確處理。要求它歸零會逼出「切在 GOP 中間」，那比重疊嚴重得多。

**間距極不均勻的片源也成立（這是最大的風險，所以特別驗過）。**
全庫 172 個受影響檔案裡有 **96 個**的 `gap_max - gap_min > 0.5 秒`，
也就是「間距均勻」不是常態。取最極端的 file 297
（`gap_min=0.959`、`gap_med=4.672`、`gap_max=10.428`，下一格 keyframe
最遠在 10.4 秒之外）實測：

```
seg100 宣告頭 734.943  →  video[734.943 .. 739.489]
seg101 宣告頭 739.238  →  video[739.238 .. 749.874]    接縫重疊 0.251 秒
seg102 宣告頭 749.666  →  video[749.666 .. 760.343]    接縫重疊 0.208 秒
```

video 起點**完全等於**宣告邊界，重疊 0.2 秒上下。
這證實 R-3-1 靠的是**查表**而不是「假設間距均勻」——
推後量在這個檔案上是 4.295 / 10.428 / 10.427 秒，每一段都不同，
而結果一樣正確。

**另一端（極密）也驗過。**file 438（`gap_min=0.133`、`gap_med=0.934`，
推後量只有 0.333~1.800 秒）：

```
seg20 宣告頭 119.133  →  video[119.133 .. 126.800]
seg21 宣告頭 126.700  →  video[126.700 .. 132.233]    接縫重疊 0.100 秒
seg22 宣告頭 132.100  →  video[132.100 .. 138.167]    接縫重疊 0.133 秒
```

**三種形狀（均勻 2.0s／極不均勻 0.959~10.428s／極密 0.133~0.934s）
都是「起點完全對齊、重疊 0.1~0.25 秒」。**

#### R-3-2 一定要一起做：`-noaccurate_seek` 讓音訊跟著對齊　【高】

只做 R-3-1 的話，音訊會**落後** 2 秒（因為 `-ss` 推後了一格，而音訊是精確 seek
的，它真的從那一格開始）：

```
只做 R-3-1        : seg100 video 頭 600.600、audio 頭 602.580   ← 反而更糟
R-3-1 + R-3-2     : seg100 video 頭 600.600、audio 頭 600.587   ← 對齊
```

`-noaccurate_seek` 讓音訊不做精確 seek，跟著容器的落點走。實測結果：

```
seg100  video[600.600 .. 606.648]  audio[600.587 .. 606.603]
seg101  video[606.606 .. 612.779]  audio[606.603 .. 612.597]   audio 重疊 0.000
seg102  video[612.612 .. 618.743]  audio[612.619 .. 618.613]   audio 重疊 -0.021
```

**音訊接縫重疊 0.000 / −0.021 秒** —— R-2-3（一）那個洞消失了。

#### R-3-2-1 短段不能推（實作時補上的保護）

只跨**一個** keyframe 的短段，「下一格」就是這一段的**結尾**，
推過去等於 `-ss X -to X` —— ffmpeg 吐出一個只有兩個封包的空殼
（實測 415,668 → 18,424 位元組），那一段的畫面整個不見。

`derive_bounds()` 在格線附近本來就會切出這種段（測試片源 20 段裡有 6 段），
所以這不是罕見情形。`seek_start_for()` 因此要收 `end`：
下一格碰到或越過 `end` 就不推。

**重疊只是瑕疵，空段是整段播不出來 —— 兩者不是同一個量級。**

#### R-3-3 一定要一起做：升 `HLS_CACHE_FORMAT_VERSION`　【高】

```python
HLS_CACHE_FORMAT_VERSION = 5    # 5 = 上階 -ss 補償回退量，音訊跟著對齊
```

`hls.py` 的註解已經寫過理由：`get_segment()` 看到 `seg-N.ts` 存在就直接回傳、
不驗內容。不升版的話既有 172 個檔案的快取分段全部留著舊內容，
**修了等於沒修**，而且會跨越重新部署存活。

後台快取面板（`42414e7`）需要能清掉 `v4_` 的殘留。

#### R-3-4 不能用的做法（實測排除）

記下來避免重複踩：

| 做法 | 為什麼不行（實測） |
|---|---|
| **無條件把 `-ss` 推後一格** | 不會退格的檔案會缺掉開頭一整格（實測 seg0 從 0.000 變成 4.880）。退格是**每個檔案的性質**，只能量，不能假設 —— 也不能用副檔名判斷（金來號那個 mp4 就是會退的） |
| 用 `ffprobe -read_intervals` 量退格 | 它跟 `ffmpeg -ss` 的 seek 語意不同：在會退格的 mkv 上照樣回 600.600，**量不到退格**。要用 ffmpeg 本身量 |
| `-ss` 加微調（+0.001~+0.1） | 落點不變，docstring 已記載 |
| 輸出端 `-ss`（`-i` 之後） | **時間戳被歸零**：video 頭變成 1.996，絕對時間軸全毀（等同 `abb729a` 的 bug） |
| 輸出端 `-ss` + `-output_ts_offset` | 雙重平移，video 頭變成 602.602（多平移一格） |
| `-start_at_zero` | 同樣歸零，video 頭 3.396 |
| `-avoid_negative_ts make_zero` | 抹掉 `-copyts` 保住的絕對位置（`abb729a` 已踩過：2:33:55 顯示成 2:03:36） |
| 回到 `-output_ts_offset start` | 退回 `190647b` 修掉的錯誤標籤 |
| 邊界改成「不對齊格線」 | ABR 偏差會累加回來（`derive_bounds` 的教訓，file 297 偏差到 2864 秒） |

#### R-3-5 程式碼落點

| 檔案 | 改什麼 |
|---|---|
| `app/db.py` | 新增 `media_file.seek_backoff`（INTEGER，1／0／NULL）；檔案變動時跟 `kf_state` 一起重置 |
| `app/keyframes.py` | 新增 `measure_backoff()`：對每個檔案實際問一次 `-ss` 的落點（**一定要用 ffmpeg，ffprobe 的 `-read_intervals` 量不到退格**）。新增 `seek_start_for(times, start, end)`：查表拿下一格，**碰到或越過 `end` 就不推**（短段推過去會變空段）。`scan_one()` 順手把 `seek_backoff` 量進 DB |
| `app/hls.py` `_produce()` | `rung == RUNG_REMUX` 且 `seek_backoff=1` 時才把 `-ss` 推到下一格，一併傳給 `build_remux_cmd()` |
| `app/hls.py` | `HLS_CACHE_FORMAT_VERSION` 4 → 5 |
| `app/media.py` `build_remux_cmd()` | 多收一個 `seek_at` 參數；`-ss` 改用它；加 `-noaccurate_seek`；docstring 補 R-2 的量測 |
| `tests/two_rung_test.py` | 攔 `subprocess.run` 驗 `_produce()` 真正送出去的指令：NULL／0 不推、1 才推、短段即使會退格也不推、下階完全不受影響 |
| `tests/keyframe_test.py` | `seek_start_for()` 的邊界案例：最後一格、兩格中間、只有一格、空表、浮點誤差、`end` 的短段保護 |

**`seek_at` 由 `_produce()` 算好傳進去，不要讓 `build_remux_cmd()` 自己查 DB。**
那個函式目前是純組指令的，讓它去查邊界表會讓它與 `_produce()` 各查一次、
兩邊可能拿到不同的結果 —— 這正是 `build_playlist()` 與 `_produce()`
已經用同一份 `bounds_for()` 避開的那個坑。

#### R-3-6 診斷：把接縫重疊納入播放器診斷疊圖　【中】

`?debugPlayer=1` 已有四類 lag 的分類。增加一項：**相鄰分段的 buffered 區間重疊量**。

價值不在修 bug，在**證明修好了**：這個症狀是間歇的、與片源相關的，
沒有數字就無法確認 172 個檔案是不是都好了。

#### R-3-7 升級路徑：既有檔案要補量退格　【高】

`seek_backoff` 是後來才加的欄位，而既有 176 個 `kf_state='ok'` 的檔案
**不會再被排進 keyframe 佇列**（那是對的，邊界表沒有變）。
不補的話它們永遠是 NULL，而 NULL 一律當作「不退」——
**這次修的重疊對它們全部不會生效**。

所以要有 `backfill_seek_backoff()`，跟 `backfill_stream_info()` 同一個位置
（`run_queue()` 開頭）、同一個理由。兩點差別：

* 它比讀檔頭貴（每檔要真的跑一次 `ffmpeg -ss`，`-frames:v 1` 只搬一個封包），
  所以排在 profile／level 後面。
* **量不出來也要寫 0，不要留 NULL** —— 條件就是 NULL，留著會每次啟動都重跑。
  寫 0 的語意（不推）正好也是量不出來時該有的保守行為。

### R-4 驗收條件

實作後的狀態記在每一項後面。

1. **量測式驗收（必要）**：file 360 的 seg100~102，
   video 起點 = 宣告邊界（誤差 <= 0.01 秒），
   video 接縫重疊 <= 0.2 秒，audio 接縫重疊 <= 0.05 秒。
   **已驗**：起點誤差 +0.000／+0.000／+0.000，
   video 重疊 0.042／0.167 秒，audio 重疊 0.000／−0.021 秒。
2. **迴歸**：file 3269（金來號）行為完全不變。
   **已驗**：`rungs_for()` 仍然只回 `[0]`（單階轉碼），這次修改碰不到它。
3. **會發上階的 mp4/mov 不可以被推壞**（實作時才發現的風險，見 R-3-1）。
   **已驗**：file 408／409／410 量到 `seek_backoff=0`、不推，
   起點誤差 ±0.000、接縫重疊 0.067~0.133 秒。
4. **自動化測試**：`_produce()` 的四種情形（NULL／0／1／短段）與
   `seek_start_for()` 的邊界案例都要有測試。
