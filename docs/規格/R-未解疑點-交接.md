## 0. 一句話

**遠端播放「每幾秒畫面往回跳」的症狀已經消失，但那是靠「遠端一律不發
remux 上階」繞過去的，不是把根因修掉。**遠端拿到的本來就只有轉碼階梯，
而症狀當時確實存在 —— 所以還有一個成因沒有被解釋。

## 1. 目前的狀態（已驗證的事實）

### 1-1 行為

```
遠端：一律 transcode-only，不把 remux 混進 ABR master
區網：mkv 不發 remux；mp4/mov 保留零轉碼（實測 65 個 = mp4 46 + mov 19）
```

實機重開後使用者確認**沒有回退**。

### 1-2 代價

```
會發上階的檔案 172 個（mkv 107 / mp4 46 / mov 19）
  遠端：172 個全部失去 remux（一律轉碼）
  區網：107 個 mkv 失去零轉碼路徑
```

### 1-3 已經修好、而且留著的東西

**`-ss` 的退格補償**（`media.build_remux_cmd()` 的 `seek_at`、
`keyframes.measure_backoff()`、`media_file.seek_backoff`）。

這一條有完整的量測支撐，而且**確實是一個真的成因**：

| 片源 | keyframe 間距 | 修前接縫重疊 | 修後 |
|---|---|---|---|
| file 360（Reacher mkv） | 均勻 2.002s | 2.044 / 2.169 秒 | 0.042 / 0.167 秒 |
| file 297 | 0.959~10.428s | — | 0.251 / 0.208 秒 |
| file 438 | 0.133~0.934s | — | 0.100 / 0.133 秒 |

三者起點誤差都是 **±0.000**（video 起點完全等於宣告邊界）。
音訊接縫重疊從「約 2 秒的洞」變成 0.000 / −0.021 秒。

**關鍵發現**：退格是**每個檔案不同的性質**，不能假設也不能用副檔名判斷。
同一份視訊 `-c copy` 換容器就會變：

```
abr.mp4  -ss 3.480 → 落點 3.480  （不退）
abr.mkv  -ss 3.480 → 落點 0.000  （退一整格）
```

而庫裡的 mp4 有的退（金來號 1136.552→1126.125）有的不退（408/409/410），
mkv 也一樣（299 不退）。所以只能對每個檔案實際量一次。

> **量退格一定要用 ffmpeg，不能用 `ffprobe -read_intervals`**（試過）：
> 兩者 seek 語意不同，`-read_intervals 600.600%+4` 在會退格的 mkv 上照樣
> 回 600.600，量不到。

## 3. 沒有解釋的疑點（← 這是我想請教的部分）

### 疑點 A（最重要）：遠端本來就只有轉碼階，為什麼會回退？

`_ABR_STEPS` 產生的轉碼階都是**固定 6 秒格線**切出來的，而且我實測過
同一段在不同階的時間戳**完全一致**：

```
720p  宣告[600.000,606.000] 實際[600.000..605.964] 起點誤差 +0.000  封包 144
480p  宣告[600.000,606.000] 實際[600.000..605.964] 起點誤差 +0.000  封包 144
```

兩階的 seg-N 是同一段影片、同樣的 PTS。**照理說 ABR 在這兩階之間切不該
產生任何位移。**

那麼在「遠端 + 有 remux 上階」的舊版本裡，回退到底是：

1. **hls.js 真的切到了 remux 階**（那就是已知的 seg-N 錯位，PR #11 擋掉了），還是
2. **轉碼階之間就會回退**（那 PR #11 只是碰巧讓症狀消失，根因還在）？

**我沒有這個資料。**使用者回報時我沒有請他開診斷疊圖，所以不知道回退發生時
有沒有伴隨 `LEVEL_SWITCHED`。

如果是 (2)，那現在的「沒有回退」可能只是因為**換了快取版本**（v4→v5）
把舊的壞分段全部作廢了 —— 而不是因為 transcode-only。

> **怎麼分辨**：`?debugPlayer=1` 開著播，記錄回退當下有沒有 LEVEL_SWITCHED。
> 或者更直接：把快取清乾淨、只留 transcode-only，看還會不會回退。

### 疑點 B：master 裡有兩階的 BANDWIDTH 一模一樣

file 360 的遠端 master：

```
BANDWIDTH=2800000  RESOLUTION=1920x960   h960_ad_b2800_c2_m0   ← 高畫質頂階
BANDWIDTH=2800000  RESOLUTION=1440x720   h720_ad_b2800_c2_m0   ← 主階
BANDWIDTH=1260000  RESOLUTION=960x480
BANDWIDTH=700000   RESOLUTION=720x360
```

前兩階的 `BANDWIDTH` 與 `AVERAGE-BANDWIDTH` **完全相同**（都是 2800000），
只有解析度不同。這是 `_high_rung()` 的設計（「只放寬解析度，不放寬碼率」），
註解寫得很清楚、是有意的。

**但 hls.js 的 ABR 是按 BANDWIDTH 選階的**，兩階宣告值一樣時，
頻寬這個維度分不出勝負。

> **這一條我查過一半，所以不確定它是不是真的問題。**播放器有開
> `capLevelToPlayerSize: true`（player.js:867），hls.js 會用元素尺寸再擋一次
> —— 所以正常情況下解析度會打破平手，不至於亂跳。
>
> 但那個 cap 是**跟著元素尺寸變動的**（全螢幕、轉向、視窗縮放都會重算，
> player.js 還特地加了 resize handler 去推它重算）。cap 邊界剛好落在這兩階
> 之間、而使用者又在改變視窗大小時，會不會反覆切換？每一次切換都是一次
> SourceBuffer append —— 如果那裡有任何時間戳誤差，橫跳會把它放大。
>
> 值得看的是實機的 `LEVEL_SWITCHED` 頻率，以及是不是集中在這兩階之間。
> 如果不是，這一條可以直接劃掉。

### 疑點 C：舊快取（v4）還在磁碟上

```
data/hls/360/v4_h0_ad_b0_c2_m1      ← 舊的 remux 分段
data/hls/360/v4_h540_ad_b2000_c2_m0
data/hls/360/v5_h1080_ad_b0_c2_m1   ← 新的
```

版本在路徑裡，所以**不會被取用**（`seg_dir()` 只會產生 `v5_` 的路徑）。

**這一條查過了，不是問題**：後台快取面板的「清殘留」
（`POST /api/admin/cache/clear-stale` → `hlscache.clear_stale()`）
正是為這件事寫的，只清不是目前版本的資料夾。純粹是磁碟空間，
按一下就好，不影響正確性。

**但它跟疑點 A 有關**：v4→v5 的升版讓所有舊分段一次作廢，
而「重開後沒有回退」可能有一部分是這個造成的，不全是 transcode-only 的功勞。
要分辨的話，得在**同一個快取版本**下比較「有發 remux」與「不發 remux」。

### 疑點 D：`seek_backoff` 的回填還沒跑完

重開時背景會自動補量（每檔一次 ffmpeg）。上次檢查還有 171 個是 NULL。
NULL 一律當作「不退格」= 不補償，所以**還沒量到的檔案，退格補償是沒有
生效的**。

現在只有區網的 mp4/mov 會用到 remux，所以影響面小；但如果將來要把 remux
開回遠端，這 171 個要先量完，否則會是「一半的檔案有補償、一半沒有」。

### 疑點 E：`abr_alignable()` 的嚴格檢查目前是死程式碼

PR #11 把它收緊了（段數必須相同 + start/end 都在 0.25 秒內），
實測 172 個裡只有 34 個能過。**但遠端現在一律不發 remux，所以這個函式的
結果沒有人在用**（只剩 LAN 的非 mkv 分支會呼叫，而那條路在上面就 return 了）。

留著是因為它是「將來把 remux 放回 ABR」的前置條件。
但要注意：**它現在沒有被實際行為驗證**，如果有 bug 不會表現出來。

## 4. 如果要把 remux 開回來，我會怎麼做

不是建議現在做，是把路徑寫下來：

1. **先取得疑點 A 的答案**（回退有沒有伴隨 LEVEL_SWITCHED）。
   沒有這個資料，任何改動都是在猜。
2. **把 171 個檔案的 `seek_backoff` 補量完**，否則補償只對一半的檔案生效。
3. **先只開區網的 mkv**（單一 rendition，沒有切階問題）——
   這是風險最小的一步，而且能驗證「退格補償在 mkv 上真的有效」。
4. 區網穩定之後，再考慮遠端：**只放 `abr_alignable()` 過關的那 34 個**，
   而且要有實機的 Frame regress 數字當驗收，不能只靠 ffprobe 量分段。
