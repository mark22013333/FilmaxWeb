## 0. 修正紀錄：v1 的風險評估錯在哪

v1 把媒體庫移植 MSSQL 評為「中偏高風險」，這個判斷錯了兩次：

1. **用了假設的規模。**「1000 影片 + 5000 相片」是編的。真實規模是
   `media_file` 109、`photo` 679、`media_item` 15、`episode` 98、`play_state` 10。
2. **假設寫入形狀不變。** 用真實筆數重算，即使完全不改架構：

   | 寫入方式 | 往返 2ms | 往返 10ms | 往返 30ms |
   |---|---|---|---|
   | 現在的一句一交易（約 1,700～2,100 次） | 3～4 秒 | 17～21 秒 | 51～64 秒 |
   | 每 300～1,000 筆一批 | 約 8 次往返，任何延遲下都是「秒」等級 | | |

「40 秒到半小時」不成立。批次寫入就解決了，不是架構障礙。

### 三點質疑的回應

- **批次寫入** — 成立。但多執行緒該加在**讀相片**那段，不是資料庫。掃描的瓶頸是
  FTP 下載與 ffprobe；對資料庫加執行緒是在優化一個批次化後已不存在的瓶頸，
  還會把「單一寫入者、無競態」推進「要處理死鎖重試」。
- **不用外鍵** — 成立。代價只有一個且可量化：要有「孤兒數量」指標當體溫計。
- **時間欄位可設計解決** — 成立，而且比預期更該修：**問題現在就在資料上發生**（見 G-2）。

### 時間欄位的裁決

兩個 agent 給了相反建議（epoch 整數 vs `DATETIME2`）。採用 **Python 端一律 epoch、
SQLite 存整數、MSSQL 存 `DATETIME2`** — 沿用 `users_mssql.py` 已在運行且有測試的做法。
決定性理由：`filmax_users` 與 `filmax_audit` 已用 `DATETIME2`，媒體庫改存 epoch 會讓
同一個資料庫有兩種時間慣例。

### 測試環境：只釘上層套件不夠（2026-09-03）

`acl_test` 與 `rescrape_test` 用 `TestClient(app, client=("127.0.0.1", 1))` 偽造來源 IP，
那個參數要 **starlette >= 0.44**（實測 0.43 沒有、0.44 有）。當時的處理是把
`requirements.txt` 的 `fastapi` 從 0.115.6 升到 0.115.14，理由是「0.115.14 帶 0.45.0」。

**那個理由是錯的。** fastapi 0.115.14 的條件是 `starlette>=0.40,<0.47`，
而 **pip 只在「已裝的版本不符合條件」時才會動一個相依套件** ——
舊 venv 裡的 starlette 0.41.3 完全合法，所以升 fastapi 之後它原封不動留著，
那兩支照樣掛。實機驗證：`fastapi 0.115.14` ＋ `starlette 0.41.3` 同時存在。

改法兩項：

1. `requirements.txt` **直接釘 `starlette==0.45.0`**。傳遞相依只要有測試在依賴它的
   行為，就不是傳遞相依，是直接相依。
2. `跑測試.bat` 在跑測試之前先比對 `==` 釘住的版本與實際裝的版本，不合就印
   `警告 套件版本不符`。**這一項是為了讓「環境不對」看起來像環境不對** ——
   否則它會表現成 `TypeError: unexpected keyword argument 'client'`，
   看起來像程式壞了，而上一次就是這樣浪費掉一輪。

### .bat 的規則要再加一條：`^` 與 `!`（2026-09-03）

上面第 2 項第一版寫成 `.bat` 裡的一行 `python -c`，在實機上直接 `SyntaxError`。
原因不是 Python，是 **cmd.exe 在把那一行交給 Python 之前先吃掉了兩種字元**：

| 字元 | 在 cmd 裡是什麼 | 吃掉之後變成 |
|---|---|---|
| `^` | 轉義字元 | regex 的 `^`（開頭）不見了；`[^\]]`、`[^\s#]` 變成 `[\]]`、`[\s#]` —— 排除變成包含 |
| `!` | `setlocal enabledelayedexpansion` 之下的延遲展開標記 | `!=` 變成 `=`，於是 `if a=b` 是語法錯誤 |

所以原本那條「.bat 內容必須是純 ASCII」要補一句：
**判斷邏輯不要寫在 .bat 的 `python -c` 裡。** 改成獨立的 `tests/pins_check.py`，
`.bat` 只負責呼叫 —— 兩個雷都不存在，而且那段邏輯可以自己測（反向驗證：
故意把釘住的版本改掉一個字，它要抓得到並回傳 exit 1）。

（檔案底部的 `!BAD!`／`!TOTAL!` 是刻意用延遲展開，那是對的；
規則是「不要出現在引號包住的 `python -c` 裡面」，不是「整個檔案不能有」。）

### 測試自己也有平台假設（2026-09-04）

`startup_test.py` 有一項「`app/` 裡不再有 `db.now()`」，第一版是 `subprocess.run(["grep", ...])`。
**這一套測試是在 Windows 上跑的，那裡沒有 `grep`** —— 實機直接
`FileNotFoundError: [WinError 2]`，而且掛在最後一項、前面全綠。

順著這條線查下去，`phase2_test.py` 有一個更糟的：

```python
# 「子行程真的死了」是用 pgrep 判斷的
alive = subprocess.run([sys.executable, "-c",
    "...subprocess.run(['pgrep','-f','time.sleep(60)'],...)"], ...).stdout.strip()
check("子行程真的死了，不是只設了旗標", not alive.strip(), alive)
```

在 Windows 上找不到 `pgrep` → 內層例外 → `stdout` 是空的 → **判定沒有殘留**。
也就是說這一項**因為錯誤的理由而通過**，真的漏掉一隻子行程時它一樣是綠的。
那比沒有這個檢查更糟：它讓人以為這件事被測過了。

兩個都改成不依賴平台工具：

| 原本 | 現在 |
|---|---|
| `grep -rn "db.now()" app/` | Python 走 `rglob("*.py")` 自己掃，順便印出檔名與行號 |
| `pgrep -f` 找殘留的子行程 | 子行程每 0.1 秒寫一次**心跳檔**；取消後記 mtime、等一秒、再比一次 —— 沒變才算真的死了 |

心跳那個版本還多驗一件事：**子行程有真的跑起來**（心跳檔存在）。
少了這一句的話，「子行程根本沒起來」跟「子行程被殺掉了」在檢查眼裡是同一件事 ——
又會變成因為錯誤的理由而通過。反向驗證過：讓子行程活著時 mtime 會變，檢查確實會 FAIL。

**規則：測試裡不要呼叫平台工具。** 需要 grep 就用 Python 掃，需要「行程還在不在」
就設計一個不依賴 OS 的觀察點。
