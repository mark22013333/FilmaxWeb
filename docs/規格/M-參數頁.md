## M. 參數頁的版面（**已實作**）

### 規劃時我算錯了一個數字，實測把整個設計換掉了

規劃時我寫「66 列裡有 19 列永遠不能改」。**這是錯的，兩個地方都錯。**

1. **UI 上根本沒有「永遠不能改」的列。** `Param.in_ui` 與 `Param.editable` 是同一個
   條件（`tier in (SECRET, HOT, NEEDS_RELOAD)`）—— Tier 0 與 Tier 4 的參數
   **完全不會出現在這一頁**。我當時是直接數 `params.py` 的登記表，
   沒有經過 `describe_all()` 的過濾。
2. **列數是 48 不是 66。**

而真正的問題是量出來才看到的。在 Yu 的機器上跑 `describe_all()`：

| | 數量 |
|---|---|
| UI 上總共 | **48** |
| 其中被 `.env` 蓋住、現在改不動 | **43** |
| 真的可以在後台改 | **5** |
| 其中 shadowed（後台存過、被 `.env` 蓋掉、所以沒生效） | 1 |

**43/48。** 這一頁九成是死掉的控制項，而它們跟能改的長得一模一樣 ——
使用者要一個一個點下去才發現打不進字。「分類放左邊」修不了這件事。

所以第一軸不是分類，是**「這一項現在改不改得動」**。

### 決定### 決定

| # | 決定 | 為什麼 |
|---|---|---|
| 1 | **參數獨立成一個分頁，左邊 sidenav 展開成二層** | 後台左邊**已經有一排 sidenav**。把分類做在「系統」分頁內部會變成兩排左欄並排，手機上還要收掉一排。二層 nav 只有一排左欄 |
| 2 | **二層 nav 的前兩項是狀態，不是分類**：「可以在這裡改」與「由 `.env` 決定」，中間一條分隔線，下面才是各分類 | 這是量測結果直接決定的（見上）。狀態是使用者真正要的第一個分岔；分類是「我要找 `FFMPEG_HWACCEL` 在哪」時才用的第二軸 |
| 2b | **被 `.env` 蓋住的列不給輸入框**，直接把生效值印在一個虛線框裡 | 給一個 disabled 的輸入框，等於邀請人去打字然後發現打不進去。而使用者打開這一頁最想知道的第一件事就是「現在到底是多少」 |
| 2c | **「要怎麼改」只在分類頂端講一次**，不在 29 列上各印一次 | 同一句話印 29 次，只會把每一列真正的資訊擠掉 |
| 3 | **批次儲存：底部 sticky「儲存 N 項變更」** | 少掉將近 200 顆按鈕。**安全上沒有代價** —— 所有 `lockout=True` 的參數（`HOST`／`PORT`／`AUTH_*`／`COOKIE_SECURE`）全都是 `ENV_ONLY`、根本不在 UI 裡，不存在「批次改壞把自己鎖在外面」 |
| 4 | **加搜尋框** | 66 項用搜尋比用分類快。分類是瀏覽用的，搜尋是「我知道我要改哪一項」用的 |
| 5 | 保留現有的 即時生效／存檔後套用／需重啟 badge、漂移橫幅、`.env` 錯字橫幅 | 這幾個做得對，是這一頁最有價值的部分 |

### 後端要動的一點

批次儲存需要 `PUT /api/params`（一次多筆），而不是前端迴圈打 `PUT /params/{key}`：

- 迴圈打會產生「前三項成功、第四項失敗」的半套狀態，而使用者只看到一個錯誤。
- 一次進來才能**先全部驗證再全部寫**，並在稽核記錄裡標成同一次變更。
- 每一個 key 仍然各記一筆稽核（誰、何時、從什麼改成什麼），這一點不變。

### 實作時踩到的一個 CSS 坑

`.param .note` 原本是 `display:flex;gap:6px`。註解只有一句話時看不出問題，
但我的鎖定說明有三個 `<code>` —— **每一段文字與每個 `<code>` 都變成一個 flex item，
排成一列不換行**，於是整段溢出格子外面，`<code>` 被壓成一個字寬的直排。
註解是文字，要用 `display:block`。

### 手機

左欄在窄螢幕收成現有的抽屜（`#menuBtn` 那一套，已經有了）；
二層 nav 在抽屜裡就是縮排一層，不需要新元件。
sticky 的儲存列固定在底部，注意要避開 iPhone 的安全區（`env(safe-area-inset-bottom)`）。
