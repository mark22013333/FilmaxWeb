## P. 瀏覽體驗改善：分頁跳頁、相片瀑布流、開關動畫（**已實作**）

### 這一章要解決什麼

三件使用者提出的體驗問題：

1. **分頁只有上一頁／下一頁**，要翻到第 20 頁得按 19 次。
2. **相片牆想要瀑布流**，可以一直往下滑到底，不必翻頁。
3. **跳出時要有動畫**，介面好看一點。

三件事的規模差很多：第 1 項是純粹的改良（沒有取捨），第 3 項是補一個現在完全
缺席的東西，**第 2 項才是真正要決定的那一個** —— 它改的是 20,033 張相片的主要
瀏覽方式。

---

### P-0. 現況（先確認要改的東西長什麼樣）

**三組重複的分頁器。**`app.js` 裡有三處各自寫了一份幾乎一樣的上一頁／下一頁：

| 位置 | 容器 | 程式碼 |
|---|---|---|
| 媒體庫 | `#pager` | `renderPager()`（`app.js` 第 128 行）|
| 相片牆 | `#ppager` | 內嵌在 `loadPhotos()` 裡（第 632 行）|
| 文件牆 | `#dpager` | 內嵌在 `loadDocs()` 裡（第 909 行）|

三份的行為已經有細微差異（媒體庫走全域的 `window.go`，另外兩個各自綁
`data-pp`）。**這一章要把它們併成一個 helper** —— 不是為了少幾行，而是因為
「加跳頁按鈕」如果要改三次，第四個列表出現時就會變成改四次。

**分頁的後端契約**（三支端點一致，不必改）：

```json
{ "total": 20033, "page": 3, "page_size": 60, "items": [...] }
```

`page_size` 上限 200（`api.py` 的 `min(page_size, 200)`），`page` 最小 1。

**相片牆現況**：`#pgrid` 是固定比例的方格
（`grid-template-columns: repeat(auto-fill, minmax(160px, 1fr))`，`.ph` 用
`object-fit: cover` 裁切），一頁 60 張。

**開關動畫現況**：

| 元件 | 現在有動畫嗎 | 為什麼 |
|---|---|---|
| 相片檢視器（PhotoSwipe） | **有** | `photoview.js` 已經接了 `thumbEl` filter，會從縮圖長出來、關閉時縮回去 |
| **條目詳情（`#overlay`）** | **完全沒有** | `.overlay{display:none}` ↔ `.overlay.show{display:block}` |

**所以「跳出時要有動畫」指的是條目詳情那個 Modal**，不是相片檢視器
（那個本來就有）。而它沒有動畫是有原因的：**`display` 這個屬性不能做 CSS
transition** —— `none` 與 `block` 之間沒有中間值。這不是「忘了寫」，
是要換一套做法才能補上。

**已經有的無障礙慣例**：`style.css` 第 408 行已經有
`@media (prefers-reduced-motion: reduce)` 區塊。這一章新增的每一個動畫
都要進那個區塊，不能只做一半。

### P-1. 可點選頁數的分頁（低風險，三個列表一起受益）

#### 版面

頁數多的時候不能全部列出來（20,033 張相片 ÷ 60 = 335 頁）。用**首末頁固定顯示
＋ 目前頁附近展開 ＋ 中間省略**的標準做法：

```
第 1 頁：   [上一頁] (1) 2 3 4 5 … 335 [下一頁]
第 8 頁：   [上一頁] 1 … 6 7 (8) 9 10 … 335 [下一頁]
第 335 頁： [上一頁] 1 … 331 332 333 334 (335) [下一頁]
頁數很少：  [上一頁] 1 2 (3) 4 [下一頁]      ← 不足以省略時就全部列出
```

- 目前頁前後各 2 頁（`window = 2`），首末頁一定在。
- 省略號是 `<span>`，**不可點** —— 有些實作讓它跳 ±10 頁，但那個行為沒有
  任何視覺提示，點下去的結果無法預期。
- 手機（`< 560px`）把 `window` 收成 1，否則按鈕會擠到換行。

#### 「跳到第幾頁」的輸入框

頁數超過 **20** 頁時，在分頁器右邊多一個小輸入框：`跳到 [___] 頁`。
335 頁的相片庫用點的還是要點很多次。

- `type="number"`、`min=1`、`max=pages`，按 Enter 或失焦時跳。
- 超出範圍就夾到邊界（輸入 999 → 跳第 335 頁），**不要當成錯誤** ——
  使用者的意思很明顯是「最後一頁」。

#### 共用 helper 的介面

```js
// 回傳 HTML 字串；呼叫端自己塞進容器並綁事件
renderPagerHTML({ page, total, pageSize, window = 2 })
// 綁事件（事件委派，一個 listener 綁在容器上）
bindPager(container, onGo)   // onGo(頁碼) 由呼叫端決定要 load 哪一個列表
```

**用事件委派而不是每個按鈕綁 onclick**：分頁器每次換頁都整個重畫，
逐一綁定等於每次換頁都建立十幾個 closure。

**媒體庫現在用的 `window.go`（全域函式 ＋ 行內 `onclick`）要一併換掉**：
行內 `onclick` 需要全域函式，而全域函式是這個檔案裡最難追的一種耦合。

#### 捲動位置

三個列表現在都用 `pageTo(loadFn, selector)`，它會**等新內容渲染完才捲**
（`app.js` 第 136 行的註解已經寫了原因：先捲的話格線會塌成「載入中」、
高度歸零、瀏覽器把捲動位置夾到 0）。跳頁沿用同一個函式，不要自己寫捲動。

### P-2. 相片瀑布流（這一章真正的決定）

#### 兩個獨立的變化，不要混為一談

「瀑布流」這個詞同時包含兩件事，而它們可以分開做：

| | 是什麼 | 現況 |
|---|---|---|
| **(a) 版面** | 不裁切，依原始長寬比排成高低錯落的欄 | 現在是正方形裁切（`object-fit: cover`）|
| **(b) 載入** | 滑到底自動載下一頁，不用按 | 現在是 60 張一頁 |

使用者的原話是「可以一直滑動到最後」，所以 **(b) 是主要訴求**，(a) 是
「瀑布流」這個詞附帶的版面期待。兩個都做，但要知道它們的風險不同。

#### (a) 版面：用 CSS `columns`，不要用 JS 定位

**決定：`column-count` ＋ `break-inside: avoid`。**

理由是**這座片庫的相片 100% 都有長寬**（實測 20,033/20,033）—— 掃描時
PIL 讀好、而且已經照 EXIF orientation 轉正過，存在 `photo.width/height`。
所以：

- `<img>` 上直接寫 `width`／`height` 屬性 → 瀏覽器**在圖片載入前就知道要留多高**，
  不會有版面跳動（CLS）。
- 這是 JS masonry 函式庫存在的主要理由（它們要等圖載完才量得到高度）。
  既然尺寸本來就有，那一整層依賴就不需要了。

長寬比分布（實測）：接近方形 13,401、直式 5,389、橫式 1,243 —— 沒有極端
長條圖，`columns` 的欄高不會差太多。

> **`columns` 的已知代價**：它是**先填滿第一欄再填第二欄**（垂直流向），
> 所以視覺順序是「由上到下、由左到右」，跟現在方格的「由左到右、由上到下」
> **不一樣**。按時間排序的相片牆上，這代表第 1～20 張在最左欄。
>
> 這是 CSS `columns` 無法改變的行為。要「橫向順序」就得用 JS 定位或
> CSS Grid `masonry`（後者 2026 年仍未普遍可用，不能依賴）。
>
> **建議接受這個代價**：相片牆的主要用途是瀏覽與找圖，不是按順序逐張讀。
> 但這一點必須在需求書寫明，不能等使用者發現「怎麼順序怪怪的」。

#### (b) 無限捲動：三個必須解決的問題

**1. 排序穩定性（會不會重複或漏掉）**

無限捲動是靠 `OFFSET` 一頁一頁往下要，如果排序有並列，兩次查詢的順序可能不同，
就會出現重複或漏掉的相片。

**已經沒問題**：`api.py` 的四種排序全都有決定性的 tiebreaker：

```
taken → sort_ts DESC, id DESC
added → added_at DESC, id DESC
name  → filename COLLATE NOCASE
size  → size DESC
```

`taken`／`added` 有 `id DESC` 收尾，不會並列。**但 `name` 與 `size` 沒有** ——
同名或同大小的相片順序不保證。

**而且這不是理論風險，這座片庫就有**（實測）：

| | 並列的組數 |
|---|---|
| 同 `filename` | **740 組** |
| 同 `size` | **325 組**（最多的一組有 3 張）|

用 `name` 排序 ＋ 無限捲動，那 740 組就是 740 個「可能重複顯示或漏掉」的點。
**這一章要順手補上 `, id DESC`**，否則無限捲動會偶發跳過相片，
而且因為 SQLite 的並列順序不保證穩定，很難重現。

> 這一項**必須排在瀑布流之前**：先做瀑布流等於先把已知會出錯的東西放上線。

**2. 記憶體（20,033 張一直滑下去）**

滑到底 = DOM 裡有 20,033 個 `<img>`。即使有 `loading="lazy"`，
節點本身也要記憶體。

**決定：不做虛擬捲動（windowing），但設一個「已載入上限」。**
載到 **2,000 張**（約 33 頁）時停止自動載入，改顯示一顆「載入更多」按鈕。
理由：真的要看第 2,000 張之後的人，用資料夾或排序找比一直滑快得多；
而虛擬捲動要處理捲動位置還原、PhotoSwipe 的 index 對應，複雜度不成比例。

**3. 跟 PhotoSwipe 的銜接**

`openPhoto(i)` 傳的是 `pstate.items` 的索引。無限捲動之後 `items` 會一直長，
**索引必須跟著累加而不是每頁重設**。現在的 `pstate.items = d.items`（直接覆蓋）
要改成 append。

`thumbEl(i)` 也要對得上：它用
`document.querySelector('#pgrid .ph[data-i="' + n + '"] img')` 找縮圖，
所以 `data-i` 必須是**累計索引**，不是頁內索引。

#### 兩種模式怎麼共存

**決定：加一個切換，預設維持現在的方格分頁。**

| | 方格 ＋ 分頁（預設） | 瀑布流 ＋ 無限捲動 |
|---|---|---|
| 版面 | 正方形裁切，整齊 | 原始比例，高低錯落 |
| 載入 | 60 張一頁 | 滑到底自動載，上限 2,000 |
| 適合 | 找特定一張、要跳到某一頁 | 隨意瀏覽 |

- 切換鈕放在排序下拉旁邊，狀態存 `localStorage`（跟現有的 `infoPref()`
  同一套做法，`photoview.js` 已經有先例）。
- **預設不改**：現在的方格是已經在用的東西，把預設換掉等於強迫所有人適應
  一個新版面。讓想要的人自己開。

> **為什麼不直接取代**：分頁在「我記得那張在第 12 頁」這種情境下比無限捲動好用，
> 而且 P-1 才剛把跳頁做出來。兩種模式各自有合理的使用情境，不是新舊替換。

### P-3. 開關動畫

#### 條目詳情 Modal（`#overlay`）—— 這是「跳出動畫」的主體

現在是 `display:none` ↔ `display:block`，**不能 transition**。

**做法**：改用 `opacity` ＋ `transform` ＋ `visibility`，並保留 `display` 之外的
可動畫屬性：

```css
.overlay{
  opacity:0; visibility:hidden;
  transition:opacity .18s ease, visibility 0s linear .18s;
}
.overlay.show{
  opacity:1; visibility:visible;
  transition:opacity .18s ease, visibility 0s;
}
.overlay .modal{
  transform:translateY(8px) scale(.98);
  transition:transform .18s cubic-bezier(.2,.7,.3,1);
}
.overlay.show .modal{ transform:none }
```

**`visibility` 的 transition delay 是關鍵**：關閉時要等淡出跑完才真的隱藏
（`0s linear .18s`），開啟時要立刻可見（`0s`）。只用 `opacity` 的話，
關閉後那一層仍然攔截滑鼠事件；只用 `display` 的話就回到不能動畫的原點。

**要順手處理的兩件事**：
- `.overlay` 現在有 `overflow-y:auto`，隱藏時仍會佔捲動 —— 加 `visibility:hidden`
  之後就不會了。
- Modal 開著時**背景不該捲動**。現在沒有處理（開著詳情滑滾輪，底下的媒體庫
  會跟著捲）。這是既有的小缺陷，在這一章一起補（`body.modal-open{overflow:hidden}`）。

#### 相片檢視器（PhotoSwipe）—— 已經有，不要動

`photoview.js` 已經接了 `thumbEl` filter，開啟時從相片牆的縮圖放大、
關閉時縮回去。**這一項不在範圍內。**

但瀑布流模式下 `thumbEl(i)` 的選擇器必須跟著改（見 P-2 的累計索引），
否則放大動畫會找不到來源縮圖而退化成淡入 —— 那會被誤認為「動畫壞了」。

#### 其他微動畫（低優先，一起做成本很低）

- 卡片 hover：`.card` 現在沒有 hover 效果，`.ph:hover img` 有
  `transform:scale(1.05)`。統一一下。
- 換頁時列表淡入（`.grid`／`#pgrid` 加一個短的 `opacity` 過場），
  掩蓋「載入中」與新內容之間的跳動。

#### 無障礙

**每一個新動畫都要進 `prefers-reduced-motion` 區塊**（`style.css` 第 408 行
已經有這個區塊，不要另開一個）：

```css
@media(prefers-reduced-motion:reduce){
  .overlay, .overlay .modal, .grid, #pgrid{ transition:none }
}
```

### P-5. 不做什麼（刻意的邊界）

- **不引進前端框架或 masonry 函式庫。**現在是原生 JS ＋ 一個 PhotoSwipe，
  加一個 Isotope／Masonry 為了一個版面不划算 —— 而且相片尺寸本來就有，
  那些函式庫解決的問題（等圖載完才量得到高度）在這裡不存在。
- **不做虛擬捲動。**理由見 P-2；改用 2,000 張上限。
- **不改預設的相片版面。**方格 ＋ 分頁維持預設，瀑布流是選配。
- **不動 PhotoSwipe 的開關動畫。**它已經是對的。
- **不做文件牆的瀑布流。**PDF 沒有長寬比可言，方格就是對的版面。
- **不做「無限捲動 ＋ 跳頁」並存。**兩者的心智模型互斥（無限捲動沒有「第幾頁」
  這個概念），硬做會得到一個兩邊都彆扭的介面。

### P-6. 驗收

新增 `tests/pager_test.py`（純函式，不需要瀏覽器）：

**分頁器（P-1）**

8. `window` 參數縮成 1 時的版面正確（手機）。

**排序穩定性（P-4-3，這一項最重要）**
9. `name`／`size` 排序在有同名／同大小的相片時，**連續兩頁不重複、不漏**
   —— 造 200 筆同大小的測試資料，逐頁取完比對集合等於全集。

**瀑布流（P-2）**
10. append 之後 `pstate.items` 的長度累加，且 `data-i` 與陣列索引一致
    （否則 PhotoSwipe 會開錯張）。
11. 載到 2,000 張時停止自動載入，出現「載入更多」。
12. 切換模式時 `localStorage` 有存，重新整理後維持。

**動畫（P-3）**
13. `.overlay` 沒有 `.show` 時 `visibility:hidden`（否則會攔截滑鼠事件）。
14. 開啟 Modal 時 `body` 有 `modal-open`，關閉後移除。
15. `prefers-reduced-motion` 區塊涵蓋所有新加的 transition
    —— 用字串比對釘住，不要靠人工檢查。

> 動畫本身（好不好看）沒辦法自動測，驗收靠實機看。測試只釘**行為**：
> 該隱藏的有沒有真的隱藏、該還原的有沒有還原。

> 實作過程中額外處理了兩件需求書沒寫到的事：
> 1. **頁碼超出範圍要夾住** —— 停在最後一頁時把相片刪掉，總數變少而 `page`
>    沒變，整排頁碼會一個都沒有「目前頁」的樣式。瀏覽器實測時才看到。
> 2. **視窗寬度變了要重畫分頁器** —— `pagerWindow()` 只在畫的當下讀一次，
>    手機橫轉直之後那排頁碼會超出畫面。加了 debounced 的 resize 重畫。
>
> 另外把 `FLOW_MAX` 從「硬上限」改成「可以按『繼續載入』推高的軟上限」——
> 上限的用意是防呆（避免不小心把兩萬張塞進 DOM），不是禁止使用者往下看。
