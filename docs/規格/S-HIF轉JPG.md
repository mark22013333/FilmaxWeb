## S. HIF 相片：收進相片庫，並可在頁面上轉成 JPG

**狀態：已實作（第 0～3 期）。** 五項待確認事項已定案（見最後一節），第 0 期的實測結果在「第 0 期結果」一節。

### 一句話

相片庫要能收 `.HIF`／`.HEIF`／`.HEIC`，瀏覽時由伺服器自動轉成 JPG 顯示；管理員可以在相片頁對**單張**或**整個資料夾**按「轉成 JPG」，轉完 JPG 留在原資料夾，原本的 HIF 依**拍攝日期**搬進同資料夾底下的 `YYYYMMDD原檔` 子資料夾。**永遠不刪除原檔。**

### 為什麼要拆成兩件事

| | 瀏覽 | 轉檔 |
|---|---|---|
| 目的 | 讓 HIF 看得到（Chrome、Edge 不能顯示 HEIF） | 把 HIF 換成通用的 JPG 檔，之後任何軟體都開得了 |
| 對來源目錄 | 唯讀，跟現在一樣 | **第一次需要寫入** |
| 誰能做 | 所有能看該資料夾的人 | 只有管理員 |
| 風險 | 解碼失敗只是看不到縮圖 | 搬錯、覆蓋、半途中斷會動到使用者的原始檔 |

瀏覽不依賴轉檔：不轉也看得到 HIF。所以先做瀏覽（第 1 期），轉檔（第 2、3 期）建在它上面。

### 現況（讀程式碼確認過）

- 掃描只收 `jpg／jpeg／png／webp`（[ftpclient.py:31](../../app/ftpclient.py) 的 `IMAGE_EXTS`，[scanner.py:264](../../app/scanner.py) 過濾），HIF 直接被略過。
- 縮圖與 preview 都用 Pillow（[photo.py](../../app/photo.py)）。Pillow 13.0.0 已裝，**`pillow_heif` 沒裝**。
- 來源有三種：FTP（ftplib）、SFTP（paramiko，[sftpclient.py](../../app/sftpclient.py)）、本機直讀（`LIBRARY_LOCAL_ROOTS`，[localfs.py](../../app/localfs.py)）。**目前三種都只有讀取，程式裡沒有任何寫入、搬移、建立資料夾的程式碼。**
- 刪除資料列的唯一入口是 `purge()`（A-4，[purge.py:101](../../app/purge.py)）。
- 掃描有全域的 `status.running`（[scanner.py:54](../../app/scanner.py)）。

### 範圍與決策

| # | 決策 | 理由 |
|---|---|---|
| S-1 | 轉檔**只能管理員做**，並且要 `.env` 明確開啟 `PHOTO_CONVERT_ENABLED=true`（預設 `false`） | 這是第一個會改動使用者原始檔的功能。沒開驗證時全區網都是管理員（見 L），所以光看角色不夠，要多一道明確的開關 |
| S-2 | JPG 寫在**原資料夾**，檔名 `<主檔名>.jpg` | 使用者要的行為 |
| S-3 | 原檔搬到**同資料夾**底下的 `YYYYMMDD原檔/`，檔名不變。`YYYYMMDD` 是**這張照片的拍攝日期**（EXIF `DateTimeOriginal`，讀不到才用檔案修改時間），同一個資料夾裡不同天的照片會進不同的子資料夾 | 同資料夾內的 rename 是原子操作，不用複製、不佔雙倍空間。依拍攝日期分，使用者之後能按日期找回某一天的原檔 |
| S-4 | **永遠不刪除、不覆蓋**。目標已存在就跳過並回報原因 | 不可逆的事不替使用者決定 |
| S-5 | 順序固定：寫暫存檔 → 驗證 → 改名成 JPG → 才搬原檔 | 任何一步失敗，原檔都還在原位 |
| S-6 | 「全部轉」只處理**目前這一層**的 HIF，不遞迴子資料夾（已確認） | 範圍可預期；要連子資料夾就各自按一次。`原檔/` 子資料夾本身不會被處理（S-7） |
| S-7 | 內建規則：名稱以 `原檔` 結尾的資料夾，掃描時整個略過 | 否則搬進去的 HIF 下次掃描又被收回相片庫，同一張照片出現兩次 |
| S-8 | 轉檔與掃描**互斥**：掃描中拒絕轉檔，轉檔中拒絕掃描 | 掃描會看到「JPG 已出現、HIF 還在」或「HIF 已不見」的中間狀態，把它當成新增或消失 |
| S-9 | 轉檔前一律先跳出確認框，寫明張數、JPG 位置、原檔去向、「不會刪除任何檔案」 | 動到原始檔的操作要讓人看清楚再按 |

### 資料結構

一次轉檔工作是一個 `ConvertJob`，每張照片一個 `ConvertItem`：

```text
ConvertJob  { id, folder, requested_by, started_at, state: running | done | cancelled }
ConvertItem { photo_id, src_path, jpg_path, archive_path,
              state: pending | converted | archived | skipped | failed,
              reason }            # skipped／failed 才有
```

`state` 只往前走：`pending → converted → archived`。`skipped`（例如已有同名 JPG）與 `failed` 是終點，不影響其他張。工作存在記憶體裡，服務重啟就消失，**不寫資料庫**；因為每一張的真實進度本來就由檔案系統決定（見「冪等」），不需要另外記。

### 每一張的處理步驟

1. 讀進 HIF 全檔（沿用現有的串流讀取，受 `MAX_PHOTO_MB` 限制）。
2. 解碼成像素，依 EXIF 轉正，輸出 JPEG，**全解析度**、保留 EXIF 與色彩描述檔（品質預設 **100**、色度不縮減 4:4:4，`PHOTO_CONVERT_QUALITY` 可調。JPEG 100 仍是有損壓縮，檔案會比 HIF 大很多，第 0 期會量出實際倍數）。
3. 寫到 `<資料夾>/.<主檔名>.jpg.part`。
4. 驗證：重新讀回來，確認能解碼、寬高與步驟 2 一致、大小大於 0。
5. 改名成 `<主檔名>.jpg`。目標已存在就停在這一步，標 `skipped`。
6. 用這張的拍攝日期建立 `YYYYMMDD原檔/`（已存在就沿用），把 HIF 搬進去。同名衝突時加 `_2`、`_3`。
7. 把 JPG 登記進相片庫，HIF 那一列透過 `purge()` 刪掉（只刪資料列，不碰檔案），這樣使用者不用等下一次掃描就看到結果。
8. 把 JPG 的修改時間設成與 HIF 相同，相片牆的排序才不會把轉好的照片全擠到「今天」。

### 冪等：中途斷掉再按一次要能接得上

每一張的狀態從檔案系統判斷，不靠記憶：

| 現場 | 判斷 | 動作 |
|---|---|---|
| HIF 在原處、沒有 JPG | 沒開始過 | 從步驟 1 開始 |
| HIF 在原處、有 `.part` | 寫到一半 | 刪掉 `.part`（這是我們自己產的暫存檔），重來 |
| HIF 在原處、有 JPG，且 JPG 內嵌的標記與這張 HIF 相符 | 步驟 5 完成、步驟 6 沒做完 | 直接搬原檔，不重轉 |
| HIF 已在 `原檔/`、有 JPG | 完成 | 什麼都不做 |
| HIF 在原處、有同名 JPG 但沒有我們的標記 | 別人的檔（例如相機同時存的 JPG） | 跳過並回報，**不覆蓋** |

**標記**：我們寫的 JPG 內嵌一段 JPEG 註解 `filmax-hif:<原檔名>:<原檔大小>`。「驗證通過」分不出相機的 JPG 與我們的 JPG（兩者寬高常常一樣），標記才分得出。同名判斷不分大小寫，也看 `.jpeg`。

### 來源寫入：FTP 與 SFTP 兩種

`app/hifconvert.py` 的 `SourceFS` 是很小的寫入介面（`listdir／exists／read／write／rename／mkdir／remove／rmdir／set_mtime`），`SftpFS` 與 `FtpFS` 各實作一份。**沒有做本機直讀那一份**：相片的讀取一直都走來源協定（`LIBRARY_LOCAL_ROOTS` 只給 ffmpeg 直讀影片用），寫入走同一條路才不會出現「讀的是 A 路徑、寫的是 B 路徑」的不一致。

- **SFTP**：paramiko 的 `putfo`、`rename`（SFTP v3 的 rename 目標存在會失敗，剛好是不覆蓋）、`mkdir`、`utime`。
- **FTP**：`STOR`、`RNFR／RNTO`、`MKD`、`MFMT`（設修改時間，不支援就略過）。
- `remove／rmdir` 只准刪我們自己的暫存（`.part`、`.filmax-probe*`），其他檔名一律拒絕。

來源帳號可能是唯讀帳號。這種情況要在**按下按鈕之前**就偵測出來（試著建立並刪除一個暫存檔），按鈕改成灰色並說明「來源帳號沒有寫入權限」，而不是做到一半才失敗。

### 介面

- **相片頁，資料夾有 HIF 時**：頂端出現一條提示「這個資料夾有 N 張 HIF」與按鈕「全部轉成 JPG」。
- **燈箱，目前這張是 HIF 時**：工具列多一個「轉成 JPG」。
- 兩個按鈕只有管理員看得到，且 `PHOTO_CONVERT_ENABLED` 沒開時不出現。
- 按下後出確認框（S-9），確認後顯示進度（第 x／共 n 張）、可取消；取消只會停在張與張之間，已轉好的不回復。
- 結束後的摘要：成功 N、跳過 N（逐筆列原因）、失敗 N（逐筆列錯誤）。
- 轉檔成功後，該張在相片牆立刻從 HIF 變成 JPG，不必重新整理或掃描。

### 瀏覽（第 1 期）

- 掃描收 `hif／heif／heic`。
- 縮圖與 preview 用解碼器轉成 JPEG，沿用現有的衍生檔快取（H）。
- `/photo/{id}/full` 對 HIF 回傳轉好的 JPEG（同樣快取），不能回原始 HEIF，因為燈箱放大時會換成 `/full`，瀏覽器顯示不了就變破圖。「下載原圖」另外提供原檔。
- 解碼失敗不能變成破圖：回傳一張佔位圖並在後台記錄，沿用現有 preview 的失敗處理方式。

### 第 0 期結果（用 Faily 裡真實的 Sony HIF 實測）

| 項目 | 結果 |
|---|---|
| 檔案本質 | 相機 ILCE-7CM2 拍的 **分塊（grid）HEVC**，10 位元 4:2:2，完整畫面 7008×3944，另含 1920 預覽與 320 縮圖 |
| ffmpeg 9.0.2 | 只解出單一塊（3520×1984），**不能用** |
| pillow-heif 1.8.1（libheif 1.23.6） | 解出完整 7008×3944，每張約 1.7 秒 |
| 色彩 | 傳輸曲線是 sRGB、BT.709，**不是 HLG**，不需要色調對應；轉出的顏色與相機內嵌預覽目視一致 |
| JPG 品質 100、4:4:4 | 25～27 MB，約為 HIF（7～8 MB）的 3.5 倍 |

決定：用 **pillow-heif**（`requirements.txt` 新增，沒裝時相片庫不收 HIF）。若日後遇到 HLG 的 HIF，轉出會偏灰，那時再加色調對應。

**掃描時間的代價**：每張 HIF 要解碼一次產縮圖（約 1.7 秒），一個資料夾 1000 張 HIF 的第一次掃描相片階段約多 28 分鐘。縮圖之後有快取，只有第一次。

### 測試重點

- 任何情況下原檔都不會被刪除或覆蓋（對每一步注入失敗）。
- 轉出來的 JPG 寬高與 HIF 相同，EXIF 拍攝時間保留。
- 沒開 `PHOTO_CONVERT_ENABLED`、不是管理員、沒開驗證時從區網別台裝置連入，三種情況 API 都拒絕。
- 掃描與轉檔同時啟動，後者被拒絕，且沒有任何檔案被動到。
- `原檔/` 底下的檔案不會出現在相片庫。
- 路徑含中文、空白、`;`、`|`（`LIBRARY_ROOTS` 的分隔符）時不出錯。

### 已確認的決策

| # | 問題 | 決定 |
|---|---|---|
| 1 | 子資料夾的日期 | **照片拍攝日期**，一個資料夾裡有多天就分多個子資料夾（S-3） |
| 2 | 「全部轉」的範圍 | 只有目前這一層（S-6） |
| 3 | 來源帳號有沒有寫入權限 | 使用者認為有，**尚未實測**。第 2 期按鈕出現前會先試寫一個暫存檔偵測，沒有權限就把按鈕灰掉並說明 |
| 4 | JPG 品質 | 越高越好：預設 100、4:4:4 |
| 5 | 相機同時存了同名 JPG | **跳過**，不轉、不搬、不覆蓋，摘要裡列出原因（S-4） |
