## N. 刮到錯的資料要怎麼修（**已實作**）

## 先回答：現在就能修，而且已經做好了

進條目 → **手動指定 TMDB** → 輸入正確片名 → 從結果挑一個 → 套用。
`POST /api/rescrape/{id}?tmdb_id=…` 會把片名、原名、年份、簡介、海報、劇照、
評分、片長、類型、演員全部換掉，並把 `scrape_state` 標成 `manual`。

旁邊的「重新刮削」是**重跑自動比對**，用在「檔名改對了、再試一次」的情況；
自動比對還是錯的話就用手動指定。

## 但有一個會讓你白做工的 bug

`scrape_state='manual'` 這個標記，**只有前端拿來決定要不要顯示「未刮削」角標。
後端完全不看它。**

`_scrape_items(force=True)`（也就是後台的「完整重掃」）的 where 是空字串：

```python
where = "" if force else "WHERE scrape_state IN ('pending','failed')"
```

實測（Yu 的資料庫）：

| | 筆數 |
|---|---|
| 一般掃描會刮（pending / failed） | 9 |
| **完整重掃會刮（where 空字串）** | **23，手動修正過的 2 筆也在裡面** |

所以流程是：你花時間把三部片一個一個指定對 → 某天按了「完整重掃」→
三部片被自動比對重新蓋回錯的答案，而且**沒有任何提示**。

> **`reparse`（重新分組）不會有這個問題。** 我一開始也擔心，但查過是安全的：
> `_upsert_item()` 認的是 `guess_key`，而手動指定不會動到 `guess_key`，
> `_load_registry()` 又是從資料庫把既有的 key 載回來 —— 所以重新分組會沿用
> 同一個條目，手動修正留著。**寫下來是為了下次不用再查一遍。**

## 還缺的三件事

### 1. 類型認錯就完全沒救

`kind`（movie / tv）**全專案沒有任何一條路徑可以改**。而 `rescrape` 是拿
`item["kind"]` 去查 TMDB 的 —— 一部電影被認成影集，你在影集裡怎麼搜都搜不到，
手動指定也沒用，因為它去查的是 TMDB 的 tv 端點。

這是「刮到錯的資料」裡最惡劣的一種：**看起來有修正功能，但那個功能對這個
錯誤完全無效**，而畫面上不會告訴你為什麼。

### 2. 只想改一個欄位卻得整筆重刮

TMDB 上的中文片名有時候就是不好（或根本沒有中譯），你只想改片名或年份。
`rescrape` 有收 `title` 參數，但前端沒有任何入口用它，而且它只改 `title`
不改 `sort_title` —— 改完排序會用舊的名字。

### 3. ffprobe 的資訊錯了沒有入口

`POST /api/probe/{file_id}` 存在，但只有兩個地方會呼叫它：
播放器發現 `probe_state != 'ok'` 時，以及後台「分析失敗」清單的「重試」。
**「分析成功但結果是錯的」沒有入口** —— 例如時長不對（VBR 的 mkv 常見）、
字幕軌少一條、HDR 判斷錯。

## 修正包（已實作）

| # | 做什麼 | 為什麼 |
|---|---|---|
| 1 | **`manual` 不被自動刮削覆蓋**：`_scrape_items` 的 force 分支改成 `WHERE scrape_state != 'manual'` | 這是唯一一項「不做就會讓使用者白做工」的。加測試釘住 |
| 2 | **後台加一個預設關閉的勾選**「連手動修正過的條目也重刮」 | 真的要換的時候要有路走。預設關閉 ＋ 二次確認 ＋ 顯示會影響幾筆 |
| 3 | **條目詳情加「類型改成影集／電影」** | 認錯類型是唯一「修正功能對它完全無效」的錯誤。改 `kind` 之後把 `scrape_state` 設回 `pending` 並立刻重刮一次 |
| 4 | **「只改片名／年份」的表單** | 不接 TMDB 也能修。`sort_title` 要跟著改，否則排序會用舊名字 |
| 5 | **檔案列加「重新分析」按鈕** | `/api/probe/{id}` 已經有了，只是沒有入口。分析成功但結果錯的時候要能重跑 |
| 6 | **後台「手動修正過」清單** | 重掃之後可以一眼檢查哪幾筆是自己修的、有沒有被動到。也讓第 2 項的勾選有東西可以對照 |

**分組錯誤（一部片被拆成五個條目、或五集被併成一部）不在這一包裡** ——
那是 C 章的題目，而且要同時重新想 `guess_key` 與 `_upsert_item` 的認人邏輯。

## 實作時挖出的第三個坑：`guess_key` 會過期

這一項規劃時完全沒想到，而它比原本那個 bug 更難查。

`nameparser.guess_key()` 的形狀是：

```
movie::某片名::2024
tv::某劇名
```

**kind 是前綴，year 是電影的第三段。** 所以：

| 動作 | 會不會讓 key 過期 |
|---|---|
| 改片名（顯示用） | 不會 —— key 裡的片名是從**檔名**算的，跟顯示片名無關 |
| 改年份 | **會** |
| 改類型 | **會** |
| 手動指定 TMDB（電影） | **會** —— 那句 UPDATE 把 year 換成 TMDB 的年份 |

key 過期的後果：下一次掃描時 `_upsert_item()` 用新算出來的 key 找不到這個條目，
**再建一個新的**，而使用者手動修好的那一筆變孤兒被 `purge.sweep` 清掉。
症狀是「我改好的片隔天變成兩筆，然後我改的那筆不見了」——
中間隔了一次掃描，幾乎不可能聯想到是改年份造成的。

**最後一列是本來就有的 bug**（手動指定 TMDB 會改年份），跟這一包一起修掉了。

`_rekey()` 從舊 key 拆出片名那一段來重組，而不是重新解析檔名 ——
片名那一段本來就是從檔名算出來的，重新解析只會多一個出錯的機會。

## 順手修掉的一個 UI bug

`confirmBox()` 的 `done()` 是**先 `m.innerHTML = ''` 再 resolve** 的。
所以 `await confirmBox(...)` 回來之後再去 `querySelector` 對話框裡的勾選，
拿到的一定是 `null` —— 症狀是「勾了也沒有生效」，而且完全沒有錯誤訊息。
加了一個 `collect` 回呼，在清掉之前把欄位讀走。

## 驗收（`tests/rescrape_test.py`，37 項全過）

```
一般掃描只刮 pending/failed · force 排除 manual · force+remanual 才包含它
remanual 只有跟 full 一起才生效
guess_key 重算：改年份／改類型／改回來／沒有舊 key 不亂猜
  並且跟 nameparser.guess_key() 的真實輸出對得上（不是我想的格式）
片名改了、sort_title 跟著改、狀態變 manual、只改片名時 key 不動
年份亂填被擋 · 片名空白被擋 · kind 只能 movie/tv · 找不到回 404
改成影集：kind 變了、key 換前綴、三個檔案都指派到集數、狀態是 manual
改回電影：集數清掉、episode_id 解開、而且是走 purge() 不是自己 DELETE
手動修正清單筆數與資料庫一致

```
