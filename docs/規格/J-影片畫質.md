## J. 影片畫質（遠端）

症狀：**在外面看片模糊。** 盤點之後這不是一個問題，是三層疊起來的：
不該重編的片子被重編了、重編時位元率上限把 CRF 蓋掉、以及編碼效率沒開滿。
三層的處理方式完全不同，順序也不能反 —— 第一層修好，後兩層對 97 部片子就自動不存在。

### 片庫的真實組成（`data/library.db`，117 個檔案）

| 容器 / 視訊 / 音訊 | 檔數 | 平均位元率 | 目前走 |
|---|---|---|---|
| mkv / h264 / eac3 | 60 | 10,076 kbps | **hls（重新編碼）** |
| mkv / h264 / aac | 34 | 2,224 kbps | **hls（重新編碼）** |
| mkv / h264 / ac3・其他 | 3 | 1,996–16,859 kbps | **hls（重新編碼）** |
| mkv / hevc（多為 10-bit，6 部 HDR） | 13 | 2,107–15,134 kbps | hls（重新編碼） |
| mp4 / h264 / aac | 7 | 17,681–22,216 kbps | direct |

解析度：33 部高 800、27 部高 960、26 部高 802、18 部 1080，只有 10 部高於 1080。
位元率：44 部落在 10–20 Mbps、29 部 5–10 Mbps、3 部超過 20 Mbps。

> **97 部是 h264 的 mkv。** 這些片子的視訊軌瀏覽器本來就吃得下，
> 卻因為裝在 mkv 裡而整個被重新編碼一次。

### 第 −1 層　片庫其實在本機硬碟上

實測那部 4K 的路徑露了餡：

```
資料庫裡的 ftp_path : /媒體資料庫/0.電影/脫韁的皮諾丘/Pinocchio…HEVC.AC3.mkv
實際檔案            : D:\1.FTP\媒體資料庫\0.電影\脫韁的皮諾丘\Pinocchio…HEVC.AC3.mkv
```

`FTP_HOST=127.0.0.1`，所以 FTP 伺服器與服務跑在同一台機器上，
FTP 根目錄 `/` 就是 `D:\1.FTP`。也就是說**片庫從來不是遠端來源，是本機硬碟**。

而目前每一段轉碼的資料路徑是：

```
ffmpeg  →  HTTP 127.0.0.1:8080/api/stream/{id}  →  FastAPI  →  FtpReadStream
        →  FTP 伺服器（loopback）  →  D:\ 上的檔案
```

**四層搬運，讀的是同一顆磁碟上的同一個檔案。** 而且每 6 秒一段就重來一次：
新的 FTP 連線、`REST` 到偏移量、重新開始讀。這也是 FTP 連線池壓力的來源之一。

改法是加一層路徑對應，讓「認得的路徑」直接走檔案系統：

```ini
# Tier 4（是路徑、會擴大信任邊界，所以只能放 .env，不進後台 UI）
LIBRARY_LOCAL_ROOTS=/=D:\1.FTP
```

`resolve_local(ftp_path)` 正規化 → 擋掉 `..` → 確認落在 root 之內 → 確認存在，
成功就回本機 `Path`，失敗回 `None` 走原本的 FTP 路徑（其他機器掛遠端 FTP 時照舊）。

一次解決的事情比預期多：

| 受益 | 變成怎樣 |
|---|---|
| 轉碼 | ffmpeg `-i D:\…` 直接讀檔，四層變一層，`-ss` 不再是 FTP 重新定位 |
| direct / remux | `/api/stream/{id}` 用 `FileResponse`，Range 由 Starlette 處理（sendfile），成本近乎零 |
| **I 節的 PDF** | 「先整檔快取再服務」那一整套設計**不需要了** —— 直接 FileResponse，PDF.js 的 range 請求打在檔案系統上 |
| 相片 preview/縮圖 | 不必為了產生衍生圖先把原圖從 FTP 拉一遍 |
| 掃描 | 不必走 FTP walk，`os.scandir` 拿 mtime 與 size，快一個數量級且沒有連線上限 |

**FTP 那條路不要拆掉**：它是「來源可以在別台機器」的抽象，而且 `LIBRARY_LOCAL_ROOTS`
沒設或對應不到時就是它在頂著。這一項是加一條捷徑，不是換架構。

#### 已實作（2026-09-03）

`app/localfs.py`：`enabled()` 與 `resolve_local(ftp_path)`，40 行、無狀態、不 import 任何
其他模組。設定在 `config.library_local_roots`，把 `LIBRARY_LOCAL_ROOTS` 解析成
**按前綴長度由長到短**排序的 `[(ftp前綴, 本機根目錄)]` —— 排序是必要的，
否則 `/=D:\1.FTP;/媒體資料庫=E:\media` 這種寫法會永遠命中 `/`。

`.env` 要加的那一行（只有這一行）：

```ini
LIBRARY_LOCAL_ROOTS=/=D:\1.FTP
```

防護（每一項都有測試，`tests/keyframe_test.py` 的 [J −1] 段）：

| 擋什麼 | 怎麼擋 | 擋不掉時 |
|---|---|---|
| `..` 逃出 root | 正規化後**任何一段等於 `..` 就直接拒絕**，不靠 `resolve()` 的結果去比 | 回 `None` |
| symlink 逃出 root | `Path.resolve()` 之後 `is_relative_to(base)` | 回 `None` |
| `\0` 截斷 | 字串裡有 NUL 就拒絕 | 回 `None` |
| 指到目錄 | `is_file()` | 回 `None` |
| 分隔線／重複斜線／`.` | 反斜線轉正斜線後正規化 | —— |

**每一種拒絕都是回 `None`，不是丟例外。** `None` 的意思是「照舊走 FTP」——
這一項的失效模式必須是「變慢」，不能是「播不出來」。

**這一步只有邊界表掃描在用。** `/api/stream/{id}` 改 `FileResponse`、掃描改
`os.scandir`、PDF 與相片衍生圖那幾項都還沒接 —— 那些各自要動自己的模組，
分開做才好回退。

**順序上的發現（會改動建議順序）**：`keyframes.source_for()` 先問 `localfs`，
問不到才回 `media.source_url()`。而 `source_url()` 是 HTTP → FastAPI → FTP → 磁碟
那四層。前置量測的 **6.2 秒／GB 是用本機路徑量的** ——
沒有第 −1 層的話，全庫 42 分鐘這個數字不成立，而且掃描期間會把 FTP 連線池吃住。
→ **第 −1 層實質上是第 0 層的前置條件**，而不是可以之後再做的最佳化。
（這與本章「建議順序」原本就把第 5 步排在第 6 步之前是一致的，
但原因不同：原本的理由是「省搬運」，真正的理由是「邊界表掃不動」。）

### 第 0 層　兩階 HLS：remux 當上階、轉碼當下階（影響最大）

`decide_play_mode()` 的最後一條是「mkv 即使是 h264/aac 也交給 HLS」。
於是 97 部 h264 走了一趟二次壓縮 —— 而二次壓縮的損失，**參數怎麼調都拿不回來**。

原本的答案是 **Direct Stream（只轉封裝，不轉編碼）**：視訊 `-c:v copy`、
音訊按需要轉成 AAC（eac3 那 60 部需要，aac 那 34 部連音訊都不用動）。
畫質等於原檔，CPU 幾乎為零。Plex 與 Jellyfin 叫它 direct stream，
跟 direct play 的差別只在容器。

**但「換成 remux」這個答案不完整**，而實機播放把缺口暴露出來了。

#### 為什麼從「三態」改成「兩階」

實測回報：**遠端播放時 4K 那幾部與高碼率 1080p 那幾部會頓，而且從頭就頓。**
拆開之後是兩個不同的成因（見 v4／v5）：4K 是**算力**（轉碼只有 1.15～1.37x），
高碼率 1080p 是**頻寬**（CRF 21 的輸出一路頂到 `REMOTE_BITRATE_KBPS` 的天花板）。

而「順的那一群」正好把觀看端的鏈路量了出來：2～3 GB 那 15 部片源中位 8,586 kbps、
輸出約 3～4 Mbps，播起來順。**也就是說觀看端下行吃得下約 4 Mbps、吃不下 12 Mbps。**

> 決策 8 解除上限的理由是「**上行** 100 Mbps 撐得住」——
> 那句話只算了自家這一端，**沒有算觀看端的下行**。
> 上限的存在理由一直都在，只是位置錯了。

這件事直接打到 remux：**remux 的畫質是免費的，頻寬不是。**
remux 是把原檔碼率送出去，對美國隊長那一部（19,886 kbps）等於要求觀看端吃 19.9 Mbps
—— 比現在轉碼還糟。所以三態的 `remux` 不是「對 97 部都對」，
它只對「鏈路吃得下原檔」的情況對。

那麼是不是該在 `decide_play_mode()` 加一個「頻寬維度」，由伺服器判斷該給哪一種？
**不要。** Netflix 部署過、在 50 萬名真實使用者上驗證過的結論正好相反：
靠估頻寬選碼率不可靠 —— 他們的真實流量裡實際容量與估計容量的比值低到 **0.03**，
要保證不卡就只能去要可用頻寬的 3%；而穩態下**根本不需要估頻寬**，
把碼率對應到**緩衝區水位**就好，估計只在開播、緩衝區還空著的時候有價值。
照這個做法，重新緩衝率降 10～20% 而穩態碼率還變高。

伺服器猜一個數字，就是他們放棄的那條路。而且更根本的問題是
**FilmaxWeb 現在只有一階，客戶端的 ABR 完全沒有作用空間**。

→ 所以答案是**兩階，讓客戶端的緩衝水位去選**：

| 階 | 內容 | 成本 | 畫質 |
|---|---|---|---|
| **上階** | remux（`-c:v copy` ＋ 音訊按需 AAC） | CPU 幾乎為零 | **等於原檔** |
| **下階** | 轉碼，**目標約 3 Mbps**（見下面的前置量測） | 只在客戶端選到它時才跑 | v5 量過的那條曲線 |

在區網自動拿到無損那一階；在外面鏈路撐得住就無損、撐不住自動掉下階 ——
**不需要任何人猜一個數字。**

> **前置量測把這句話修正了一半。** 上階要宣告的是**峰值**，實測 **21,703 kbps**
> （平均 10,899，峰值是平均的 **1.99 倍**）。而觀看端的鏈路約 4 Mbps ——
> 也就是**上階在遠端實際上永遠不會被選中**。
> 兩階真正的價值因此是「**區網無損且零轉碼 ＋ 遠端一階乾淨有界的轉碼**」，
> 而不是「遠端有時候能拿到無損」。遠端仍然發兩階（哪天在很快的網路上 ABR 爬得上去），
> 但不要把它當成常態。

#### Master playlist 的形狀

`hls.py` 的 `build_master()` 現在就已經在發 master playlist，只是裡面只有一個
`EXT-X-STREAM-INF`。兩階是**擴充這個函式**，不是新架構：

**區網**（`is_local_network()`）只發上階 —— 不需要 ABR，也就完全不會碰到轉碼器：

```m3u8
#EXTM3U
#EXT-X-VERSION:3
#EXT-X-STREAM-INF:BANDWIDTH=21895000,AVERAGE-BANDWIDTH=11091000,RESOLUTION=1920x960,CODECS="avc1.640029,mp4a.40.2"
index.m3u8?p=h0_a0_b0_c2_m1
```

**遠端**發兩階：

```m3u8
#EXTM3U
#EXT-X-VERSION:3
#EXT-X-STREAM-INF:BANDWIDTH=21895000,AVERAGE-BANDWIDTH=11091000,RESOLUTION=1920x960,CODECS="avc1.640029,mp4a.40.2"
index.m3u8?p=h0_a0_b0_c2_m1
#EXT-X-STREAM-INF:BANDWIDTH=3492000,AVERAGE-BANDWIDTH=3192000,RESOLUTION=1920x960,CODECS="avc1.64001f,mp4a.40.2"
index.m3u8?p=h1080_a0_b3000_c2_m0
```

（`BANDWIDTH` 都已經含音訊：AAC 192 kbps。上階 21,703＋192、下階 `maxrate` 3,300＋192。）

#### 分段邊界：上階由 keyframe 決定，下階獨立

`build_playlist()` 現在從 `duration` 算固定 6 秒邊界，第 i 段就是 `[i*6, (i+1)*6)`。
**上階不能這樣切** —— `-c:v copy` 只能從 keyframe 開始，而 `i*6` 幾乎永遠不落在 keyframe 上。
`-force_key_frames` 在 copy 模式下無效。所以上階的邊界只能由 keyframe 決定：
每段取「湊滿 ≥ 分段長度的最少 keyframe 數」。

**原本的設計是「下階跟著上階的邊界」**，理由是 HLS 要無縫切換就得兩階邊界一致。
**前置量測推翻了這個取捨**：

* 上階的邊界讓段長變成 **7.34 秒**（keyframe 中位 3.17 秒 × 2），比設定的 6 秒長 22%。
* 而下階是**遠端唯一會用到的那一階**（上階峰值 21.7 Mbps，遠端選不到）。
  4 Mbps 的鏈路下，一段 3 Mbps × 7.34 秒 ≈ 2.8 MB，光下載就 5～6 秒，
  hls.js 要兩段才起播 —— 段變長，開播就等更久。
* 而「無縫切換」的價值同時變小了：區網一直是上階、遠端一直是下階，
  **切換只發生在鏈路剛好落在 3.5 與 21.9 Mbps 之間的窄帶上**，很少見。

→ **兩階各自用自己的邊界。** 上階照 keyframe，下階維持固定的短段。
切換時 hls.js 會做一次 seek，可能看到一次短暫停頓 —— 用一個罕見事件的一次停頓，
換常態路徑的開播速度，這個交換是划算的。

**兩階的解析度與編碼相同**（1920×960、h264 + AAC），所以切換的成本只是那次 seek，
不涉及 MSE 的 codec 切換 —— 這是這個交換能成立的前提，換片源要重新確認。

remux 不可行的片源（4K DV 那部：keyframe **10.01 秒** > 6 秒、三行 DTS 警告）
**只發下階**，邊界就是現在的固定 6 秒 —— 它不需要 keyframe 表。

#### BANDWIDTH 與 CODECS 怎麼填（兩個最容易寫錯的地方）

**`BANDWIDTH` 要填峰值，不是平均。** HLS 規格的 `BANDWIDTH` 是「單段的峰值位元率」，
而 remux 的峰值遠高於平均：**全檔實測 21,703 kbps 對平均 10,899 —— 1.99 倍。**
**填平均的後果是 hls.js 在 12 Mbps 的鏈路上會選上階，然後在每個峰值卡一次** ——
那比不給上階更糟。峰值從 keyframe 掃描順便拿到（同一次 `ffprobe` 要
`pts_time` 也要 `pos`，相鄰兩點的位移就是段大小）。`AVERAGE-BANDWIDTH` 另外填平均。
兩者都要加上音訊碼率。

下階的 `BANDWIDTH` 填 **VBV 上限**（`maxrate`，也就是保證的天花板），
`AVERAGE-BANDWIDTH` 填目標碼率。

**`CODECS` 寫錯會讓 Safari 直接拒收那一階。** 現在是寫死
`avc1.64001f,mp4a.40.2`，那是 High profile / level 3.1 —— 上階是原檔照抄，
profile 與 level 由片源決定，寫死一定有片源不符。
→ 從 `ffprobe` 的 `profile`／`level` 推出正確的字串；**推不出來就整個屬性省略**
（規格允許省略），不要猜。兩階的音訊都是 AAC，所以 `mp4a.40.2` 都對。

`RESOLUTION`：上階是片源解析度，下階是縮放後的。

#### 實作進度：第 4 項「邊界表」已完成（2026-09-03）

上面那張表的第 4 項做完了，其餘五項還沒動。這一項先做，是因為它**完全不碰播放路徑** ——
播放器看不到它，做壞了最多是「上階沒有邊界表所以只發一階」，也就是現在的行為。

**資料形狀**（`app/db.py`）

| 放哪 | 是什麼 |
|---|---|
| `media_file.kf_state` | `pending` / `ok` / `skipped` / `failed`，預設 `pending` |
| `media_file.kf_error` | 失敗或跳過的原因（`skipped` 也一定要寫，見下） |
| `media_keyframe` | `file_id`（PK）· `times`（JSON 陣列）· `positions`（JSON 陣列）· `count` · `gap_min/med/max` · `updated_at` |

**存原始資料，不存算好的邊界。** 邊界規則還沒定案（「湊滿 ≥ 分段長度」讓 6 秒變成
7.34 秒，另一種是取「離目標最近」），而重掃一次是 42 分鐘。存 `times` 與 `positions`，
換規則只要重跑 `derive_bounds()`。

**失效跟探測吃同一個訊號。** `_FILE_UPSERT` 的 `ON CONFLICT` 子句原本只把
`probe_state` 打回 `pending`，現在同一句順手把 `kf_state` 也打回去、清掉 `kf_error`。
不另外寫一套偵測 —— 檔案變動的判斷只該有一份。
`table_for()` **只在 `kf_state='ok'` 時回表**，其他狀態一律回 `None`：
`pending` 代表「這份表可能是舊檔案的」，照著它切分段會切出對不上的段。

**孤兒。** `purge.py` 跟著刪 `media_keyframe`（A-4 的單一刪除進入點，形狀跟
`play_state` 那句一樣）。測試會先確認那一列存在、purge 之後不存在 ——
只驗「不存在」會被「本來就沒寫進去」騙過。

**`ffprobe` 要怎麼問**（這一題花的時間比預期多）

```
-skip_frame nokey -show_entries frame=pts_time,pkt_pos
```

* 欄位名是 **`pkt_pos`，不是 `pos`**。`frame=pts_time,pos` 只吐得出時間，
  偏移那一欄是空的 —— 而偏移是 `BANDWIDTH` 峰值的唯一來源，缺了就白掃。
* `pkt_pos` 的值與 `-show_packets` **完全一致**（ffmpeg 6.1 與 n9.0 都驗過），
  所以不需要為了拿偏移多跑一次 `-show_packets`。
* `-skip_frame nokey` 是速度的關鍵：解碼器只吐 keyframe，6.2 秒／GB 就是這樣來的。

**背景佇列的四條規則**

1. **不是掃描的第四階段。** 掃描結束（`status.note("掃描完成")` 之後）才啟動，
   `scanner.py` 只多一行 `keyframes.start_background(cancel=_cancel)`。
   探測是每檔一秒級、CPU 為主；這一階是每檔 30 秒、純 I/O。混在一起會讓
   「掃描」從幾分鐘變成 45 分鐘 —— 那是性質改變，不是變慢。
2. **並行度固定 1，不吃 `PROBE_CONCURRENCY`。** 這一階讀的是轉碼器同時在讀的那顆磁碟，
   開多條只會互相拖慢（`hls.py` 的註解已經為這件事付過學費：
   「同一個檔案單獨跑 1.9 秒，三個並行時變成 10.9 秒」）。
3. **只排 h264。** 其他編碼（那 13 部 hevc）沒有上階可給，直接標 `skipped`
   **並寫進 `kf_error`** —— 留空白的話，將來看到空的會誤判成「還沒跑到」。
4. **只排 `probe_state='ok'` 的。** 還沒探測完就沒有 `video_codec`，排了只會失敗。
   另外有 `request_soon(file_id)` 讓開播中的檔案插到最前面。

可取消（每一段前後都看 `cancel.is_set()`）、可續跑（狀態在 DB，重啟接著跑）、
`limit` 參數讓測試能只跑兩個。

峰值 vs 平均、狀態機與失效、purge 孤兒、佇列的 limit／插隊／優先／取消，
以及**真的用 `ffprobe` 掃一個檔案**（沒有 ffmpeg 的機器會跳過而不是失敗）。

#### 實作進度：第 1～4 項 ＋ 速度樣本已完成（2026-09-03，第一批）

**開關是 `HLS_TWO_RUNG`，預設 `false`。** 關著的時候 `rungs_for()` 只回下階 ——
也就是現在的行為。這不是暫時的鷹架：remux 的時間戳行為要在真實片源上驗過才敢開，
而開關也是出問題時的退路（後台即時生效，不必重開服務）。

| 項 | 做了什麼 |
|---|---|
| 1 | `profile_key()` 加 `m0`／`m1`；`_parse_profile()` 認得它。**沒寫 `m` 的舊網址一律當下階**，相容且安全 |
| 2 | 新的 `rungs_for(file_id, duration)` —— 「有哪幾階」只有這一個答案來源 |
| 3 | `build_master(file_id, profile, remote, duration)` —— 區網一階、遠端兩階 |
| 4 | `build_playlist()` 上階吃邊界表；`bounds_for()` 每次算，不另外存 |
| 7 | `should_record_speed(rung, background)` —— 上階的耗時不進速度樣本 |

**`rungs_for()` 給上階的四個條件**（缺一個就只發下階）：
`HLS_TWO_RUNG` 開著 · `kf_state='ok'` · **keyframe 中位間距 ≤ 分段長度** · 邊界表算得出邊界。
第三個條件就是 4K DV 那部被排除的地方（10.01 秒 > 6）—— 間距比分段還大的話，
每段只裝得下一個 keyframe，段長會被片源綁死。

**`TARGETDURATION` 要照實際最長段填，不能填設定值。** 上階實測是 7.25～7.34 秒
而設定是 6 —— 填 6 是規格違反（HLS 規定 `TARGETDURATION` 不得小於任何一段的長度）。

**`CODECS` 的資料從哪來。** `media_file` 原本沒有 profile／level 兩個欄位，
所以補上 `video_profile`／`video_level`，**由 keyframe 掃描順手寫進去** ——
那支掃描本來就在對同一個檔案跑 ffprobe，而且它跟邊界表是同一組前置條件。
問不到就兩欄留 NULL，`codecs_attr()` 回 `None`，那個屬性整個省略（規格允許）。
`avc1.PPCCLL` 的對照表只放認得的五種 profile，**認不得不猜** ——
省略只是少一點資訊，填錯是整階在 Safari 上不能播。

**profile key 換形狀 → 舊快取清一次。**`PROFILE_KEY_VERSION=2` ＋ `kv` 版本號，
啟動時 `migrate_cache()` 清一次就記下來。舊分段不會被誤用（名字對不到），
但會一直佔著 `HLS_CACHE_MAX_MB` 的額度直到 LRU 汰掉它們 ——
而在那之前，真正在用的分段可用的空間就變小了。

**上階也不排預轉。**預轉存在的理由是「轉碼跟不上播放」，而 remux 是 17x；
它需要的是磁碟頻寬，那正好是使用者正在播的那一段也需要的東西。

#### 實作進度：第 5～6 項已完成（2026-09-03，第二批）

**`build_remux_cmd()` 是獨立的一支，不是 `build_transcode_cmd()` 的一個分支。**
兩者共用的部分（來源、`-ss`／`-t`、`-map`、mpegts 輸出）不到一半，
而不共用的部分是「絕對不能出現」的那些：`-vf`、編碼器參數、`-profile:v`／`-level`、
`-force_key_frames`、`-sc_threshold`。混在一個函式裡用 `if` 擋，
將來加一個轉碼參數就有機會漏進 copy 的路徑 —— 而那不會報錯，
**只會讓「零損失」這句話悄悄變成假的**。測試裡有九項專門檢查這些旗標不存在。

三個關鍵參數：

| 參數 | 為什麼 |
|---|---|
| `-ss` 在 `-i` **前面** | 輸入端 seek。copy 只能從 keyframe 起頭，而 `start` 就是邊界表裡的 keyframe 時間戳，兩者剛好吻合。放到輸出端 seek 會變成每段都從 0 解一次 |
| `-avoid_negative_ts make_zero` | mkv 有一整類片源 DTS 不單調（量測工具在那部 4K DV 上吃過三行警告），copy 模式下 mpegts muxer 會直接拒收。make_zero 讓它平移到零而不是拒收，再由 `-output_ts_offset` 放回這一段該有的位置 |
| 音訊按需 | ac3／DTS／TrueHD 一定要轉 AAC（瀏覽器不吃）。**已經是 AAC 也要看聲道數** —— 5.1 的 AAC 直接 copy 會讓 `AUDIO_CHANNELS` 的降混在上階整個失效，而那個設定存在的理由就是多聲道 AAC 在 mpegts 裡各家支援度不一致 |

**零損失是驗過的，不是推論的。**測試會真的產生一段上階，然後把它解碼出來的
逐格 md5 跟原始檔同一段比對 —— 完全相同。段裡的畫格只會多不會少
（`-t` 按時間截、copy 收在封包邊界），段長誤差在 0.35 秒內。

**一段失敗 → 整個檔案的上階下線。**`remux_state`／`remux_error` 兩個欄位，
`rungs_for()` 看到 `failed` 就只回下階，master 改發單階，**播放不中斷**。
刻意**不做**「退回 CPU 重試」：copy 根本沒用到編碼器，再試一次只會再失敗一次 ——
失敗的原因是片源本身（DTS、時間戳、容器），那是整個檔案的性質。
下線會寫進後台「媒體庫」頁的**原畫質直送下線**清單（另外加了一張
**邊界表掃描失敗**的清單）。這條路徑的性質是「安靜地降級」——
使用者只會看到畫質從原檔變成轉碼，不會看到任何錯誤，
**所以那張清單是把這個功能開起來的條件之一**。檔案變動時
`remux_state` 跟 `kf_state` 吃同一個 `ON CONFLICT` 訊號一起清掉。

**遠端不再走 `direct`，但只在真的有上階時。**那 7 部 mp4 裡有 7.6 GB／4,661 kbps
與 4.8 GB／4,508 kbps 兩部大檔，`direct` 沒有階梯可以降。改走兩階之後上階
畫質一樣是原檔，不夠時客戶端自己降。**沒有上階就不要改** ——
把遠端的 direct 換成「一定重編」是退步。

**開播插隊真的接上了。**`request_soon()` 原本沒有任何地方呼叫。現在 master
端點會在 `kf_state` 還是 pending／failed 時把它插到最前面，並且順手
`start_background()` —— 佇列是掃描結束時啟動的，那條執行緒早就跑完了，
插了隊沒人處理的話插隊永遠不會生效。**不等它算完**（一個檔案 30 秒）。

**升級回填。**profile／level 是後來加的欄位，而 `kf_state='ok'` 的檔案不會再
被排進佇列（那是對的，邊界表沒變）。所以另外有 `backfill_stream_info()`：
只讀檔頭、不解碼、毫秒級，把 `video_profile IS NULL` 的補起來。
問不到就寫 `unknown` 這個 sentinel —— **不能留 NULL**，否則那個檔案
每次啟動都會被重新問一次，而且永遠問不出來。

#### 這個設計順手逼出兩個現存缺陷

> **兩項都處理了（2026-09-03）**：第 1 項用「排除上階」那個較小的做法
> （`should_record_speed()`），第 2 項在 `play_info` 裡改掉，
> 但只在真的有上階時 —— 見上面的第二批。

**1. `_speed_samples` 是全域的。** `record_speed()` 記的是「最近 8 段的轉碼速度」，
不分檔案也不分 profile。remux 一段只要 0.35 秒（6 秒影片 ÷ 0.35 ≈ 17x），
這種數字灌進去會讓 `_schedule_prefetch()` 以為機器很閒，
於是在 4K 那種 1.2x 的片子上照樣開預轉 —— 而註解裡已經寫過那個後果
（「同一個檔案單獨跑 1.9 秒，三個並行時變成 10.9 秒」）。
→ **速度樣本要按 (file_id, profile) 分開**，或至少把 remux 那一階排除在外。

**2. `direct` 模式在遠端沒有退路。** 那 7 部 mp4 走 `direct`，其中有 7.6 GB／4,661 kbps
與 4.8 GB／4,508 kbps 兩部大檔。`direct` 沒有階梯可以降，鏈路不夠就只能卡。
→ 遠端不該選 `direct`，應該一律走兩階 HLS（上階就是 remux，畫質一樣是原檔）。

#### 成本模型，以及一個誠實的修正

上階幾乎不花 CPU，下階「只在被選中時才跑」—— **但這句話要打折。**
hls.js 預設 `startLevel: -1`，開播時用一個保守的初始頻寬估計挑階，
**實際上會從最低階開始**再往上爬。所以下階在幾乎每一次開播的頭幾段都會被產生。

兩個處理方式，都很便宜：

* **區網只發一階（上階）—— 這是規則，不是最佳化。** `auth.py` 已經有
  `is_local_network()`。區網不需要 ABR，發單階就完全不會碰到轉碼器 ——
  「在家看片」因此是**零轉碼路徑**，而這是整個設計最確定會兌現的那一塊。
* 遠端保留兩階，但在前端設 hls.js 的初始估計值，不要讓它從最低階起步。
  遠端的常態是下階，所以下階的段長與目標碼率要按「開播要快」來調，
  不要按「畫質上界」來調。

#### 這個設計**不解決**什麼

**4K 那 6 部。** 它們的瓶頸是算力：x264 1.15x、NVENC 1.37x，
而且瓶頸在 4K HEVC 10-bit 的 CPU 解碼 ＋ zscale tonemap，不在編碼器 ——
**降低目標碼率不會讓它變快**。它們也沒有上階可以給（DV 那部連 remux 都不行）。
唯一的槓桿是 **libplacebo 的 GPU tonemap**（ffmpeg 8.1 已經帶了，還沒量）。
兩階 HLS 對這一群的貢獻是零，不要指望。

#### 前置量測結果（2026-09-03，`測試分段邊界.bat`）

動工前要確認的三件事都有答案了。工具：`app/vidprobe.py --keyframe-scan`。

| | Dark Matter（4.5 GB、53 分） | 皮諾丘 4K（5.5 GB、82 分） |
|---|---|---|
| `-show_packets` | 30.0 秒 | 52.4 秒 |
| `-skip_frame nokey` | **28.8 秒** | **33.5 秒** |
| keyframe 數（兩種問法） | 1074／1074 **一致** | 493／493 **一致** |
| 間距 最短／中位／最長 | 0.167／3.17／3.963 | 9.927／10.01／10.052 |
| 可對齊 6 秒分段 | **是** | **否** |
| 段數 · `#EXTINF` 中位 | 438 · **7.341 秒** | 492 · 10.01 秒 |
| 視訊峰值／平均 kbps | **21,703／10,899（1.99×）** | 17,172／9,665（1.78×） |
| 邊界表大小 | 4,187 bytes | 4,777 bytes |

**1. 成本：約 6.2 秒／GB，`-skip_frame nokey` 比較便宜。**
兩種問法算出來的 keyframe 數完全一致，所以挑便宜的就好（hevc 上差距特別大 ——
`-show_packets` 要吐出所有封包的文字）。換算全庫 147 檔／408 GB ≈ **42 分鐘**，
只算 h264 那 133 檔／350 GB ≈ **36 分鐘**。
→ **邊界表只能在掃描時算，而且要走背景佇列**，不能塞進掃描迴圈。

**2. 全檔掃描修正了視窗抽樣。** v3／v4 是拿 180 秒的視窗量的：

| | 180 秒視窗 | 全檔 |
|---|---|---|
| keyframe 數 | 53 | 1074 |
| 間距 最短 | 1.376 | **0.167** |
| 間距 中位 | 3.629 | **3.17** |
| 間距 最長 | 3.963 | 3.963 |

最短間距差了 8 倍。**結論本身沒變**（最長 3.963 < 6，可對齊），
但這是「抽樣一段不等於全檔」的具體案例 —— 而我們原本正是拿那個視窗在判 remux 可行性。

**3. 峰值是平均的 1.99 倍**，這一項改了設計（見上面「兩階」那張表下的註）。

**還在猜的一個數字：觀看端的下行。** 下階的目標碼率（約 3 Mbps）是從
「2～3 GB 那一群播起來順、輸出約 3～4 Mbps」推的，不是量到的。
真要定案得在觀看的那台裝置上量一次下行（WARP 開與關各量一次）。
**這是本節唯一還在推論上的數字。**

#### 失敗與退回

remux 會遇到非單調 DTS 與時間戳問題（Jellyfin 有一整串同類 issue）。
`_produce()` 已經有「硬體編碼失敗就退回 CPU」的形狀，remux 照同一個形狀做：
**某一段 remux 失敗 → 那個 file_id 的上階整個下線**（改發單階 master），
不是只退那一段 —— 一份播放清單裡混著 copy 與重編的分段是更糟的失效。
退線要進 `audit`，後台看得到清單，才敢把這條路開起來。

#### 刻意不做

* **三階以上。** 即時轉碼多一階就多一份算力，而 v5 量到 2.8→12 Mbps 的
  VMAF 差距不到一個 JND（Netflix 的刻度是 6 分 ≈ 1 JND，我們量到 4.9 分）——
  中間再插一階買不到可感知的差異。
* **離線預轉整個片庫。** 那與本節的結論（不要重編）直接矛盾，
  而且要先把幾十 GB 搬一遍。只有那 2～3 部「原檔碼率遠端吃不下」的片子
  值得考慮預先做一份下階，等真的變成問題再說。
* **per-shot／Dynamic Optimizer。** Netflix 自己說計算量「遠高於」2-pass，
  靠離峰時段的閒置雲端機器跑。這台要即時服務，沒有這個餘裕。
* **fMP4 + byte-range。** 量測顯示照 keyframe 切就夠了（備案，留給 keyframe
  間距超過分段長度的片源）。

#### 開起來的步驟

1. **先讓邊界表掃完。** 服務重開一次（會自動 `ALTER TABLE` 補四個欄位），
   掃描結束後背景佇列會把 `kf_state='pending'` 的排掉，另外把既有檔案的
   profile／level 回填（毫秒級，不是重掃）。後台「媒體庫」頁看得到失敗清單。
2. **`HLS_TWO_RUNG=true`** —— 後台參數頁「轉碼」分區，即時生效，不必重開服務。
   出問題就關回去，那一刻起就是原本的行為。
3. 照下面的驗收清單走一次。**最重要的是第二項與第五項**：
   區網要完全沒有 ffmpeg 被啟動、遠端限速要停在下階而不中斷。
4. 開起來之後看一次後台的「原畫質直送下線」清單。**空的才算過** ——
   那條路徑會安靜地降級，清單是唯一看得到的地方。

### 量測結論的套用（2026-09-03，第 4.6 步）

量完之後有兩件事要分開：**值**（`.env`）與**機制**（`media.py`）。值只要貼；
機制得改，因為原本的程式碼**沒有辦法表達「綁碼率」這件事**。

#### `.env` 的五行

```ini
X264_PRESET=medium
REMOTE_BITRATE_KBPS=8000
NVENC_CQ=25
TRANSCODE_CRF=17
FFMPEG_HWACCEL=nvenc
```

`.env.example` 的預設值也一起改成這一組（乾淨安裝就是量出來的設定，不是舊的猜測值）。

#### `media.py`：位元率控制從「一律綁品質」改成「有目標就綁碼率」

原本的形狀是：畫質參數永遠是 `-cq`（NVENC）或 `-crf`（x264），
遠端時**在外層另外補**一組 `-maxrate`／`-bufsize`。兩個問題：

1. **cq 導向給不出上界。**同一個 `-cq` 在不同片源上吐 1,093 到 10,195 kbps 都有 ——
   而兩階 HLS 的下階要在 master playlist 宣告 `BANDWIDTH`，
   那是**承諾**的上界。承諾不出來，這一階就不能發。
2. **v4 量到 cq 模式下「更多碼率、更低分」的異常**（cq 28：「調滿」3,305 kbps→92.8
   對「現況」2,579 kbps→94.0，疑似 `-spatial-aq`，仍未查明）。
   綁碼率的兩條階梯不受它影響 —— v4／v5 兩條獨立階梯在同碼率上量到同一個分數
   （差 0.1～0.4），這是這個改法的依據。

改法是把「位元率怎麼控制」抽成一個 `_rate_args(encoder, target_kbps)`：

| | 有目標碼率（遠端） | 沒有目標碼率（區網重編） |
|---|---|---|
| NVENC | `-b:v Nk -maxrate Nk -bufsize 2Nk`，**不給 `-cq`** | `-cq 25 -b:v 0`（`-b:v 0` 少了 cq 就失效） |
| x264 | capped CRF：`-crf 17 -maxrate Nk -bufsize 2Nk` | `-crf 17` |

**外層不再自己補 `-maxrate`。**「上限」與「目標」是同一件事的兩面，
分兩個地方加會出現 `-maxrate` 兩次、後者靜默勝出 —— 這種 bug 不會有錯誤訊息。
測試裡有一項專門盯這個（每個旗標最多出現一次）。

**階層記憶沒有被破壞。**`_test_encoder()` 記的是「哪一層通過」（標籤），
不是那一串數字 —— 這是既有設計，為了讓後台改 `NVENC_CQ` 之後立刻生效。
`target_kbps` 只換掉那一層裡的位元率參數，**層級的名字與數量不變**，
所以「探測時沒有目標碼率、實際轉碼時有」仍然對得上同一層。
（`僅 cq` 這個層名改叫 `僅品質` —— 碼率導向時那一層裡沒有 cq。標籤只存在記憶體裡。）

#### 順手抓到一個設定漂移

`FFMPEG_HWACCEL` 的預設值**兩邊不一致**：`params.py` 與 `.env.example` 都寫 `auto`，
而 `config.py` 真正讀的是 `none`。也就是後台參數頁顯示的「預設值」是假的，
而乾淨安裝實際上走 CPU 編碼 —— 正好與結論 (a)（重編首選 NVENC）相反。
`config.py` 改成 `auto`（`resolve_hwaccel()` 本來就會實測、失敗自動退回 libx264，
所以 auto 是安全的），並在測試裡加一項「註冊表宣告的預設值要等於程式碼的預設值」。

#### 測試

`tests/encoder_args_test.py`，29 項。不需要 ffmpeg（把 `pick_option` 換成假的），
所以沒有顯卡的機器也跑得完、也不會因為某台機器的 NVENC 選項不同而變紅。
全套 **593 通過、0 失敗**。

#### 還沒動的

* **`-multipass`、`-spatial-aq`、libplacebo GPU tonemap** —— 三個都沒量，量之前不動。
* `TRANSCODE_CRF=17` 仍然是暫定值（v5 的 x264 曲線是用 `veryfast` 量的）。
  要確定就在 preset 改成 `medium` 之後重跑 `測試畫質-CRF.bat`（約 25 分鐘）。
  **優先度不高**：NVENC 是預設路徑，x264 只是退路。

### 畫質標示：級別依寬度，不依高度（2026-09-03）

開起來之後回報「畫質只有 804p」。**查下來畫質沒問題，是標示在誤導。**

```
id 297  Captain.America.Brave.New.World.2025.BluRay.1080p...x264.mkv
        1920 × 804   h264   17.7 GB   19,886 kbps
```

804 是**片源本身的畫面高度** —— 2.39:1 的寬螢幕片，黑邊在壓製時就裁掉了。
檔名裡的「1080p」是級別不是高度。程式這邊不可能製造出 804：
縮放只看高度而且只會變小（`out_h = min(want, src_h)`），要縮也是縮成 720。

片庫的高度分布證實這是常態而不是特例：

| 高度 | 部數 | | 高度 | 部數 |
|---|---|---|---|---|
| 800 | 33 | | 720 | 14 |
| **1080** | **32** | | 1920（直式／4K 直放） | 6 |
| 960 | 27 | | 2160 | 3 |
| 802 | 26 | | 804 | 2 |

**真正 1920×1080 的只有 32 部，而 1920 寬但高度不是 1080 的有 88 部。**
照高度標的話，那 88 部全部看起來像被降級。

改法：`media.quality_class(width, height)` **依寬度判級別**
（1920 → 1080p、3840 → 4K；Plex／Jellyfin 也是這樣），
`media.scaled_size()` 算出每一階縮放後的實際解析度，
`/api/play/{id}` 多回 `quality.levels`（每階的級別＋實際解析度）與
`quality.source`。播放器三個地方一起改：畫質選單（`原畫質 1080p`、
每階顯示 `720p 1718×720`）、切換提示、片源資訊那一列（`1080p · 1920 × 804`）。

**級別與解析度兩個都要給**：級別讓人知道「這是哪一檔的畫質」，
解析度讓人知道「實際上是什麼」。只給其中一個都會回到同一種誤會。

`quality.ladder` 保留不動 —— 前端可能是快取的舊版，少一個 key 會讓畫質選單整個不見。

### 第 1 層　位元率上限把 CRF 蓋掉

你的 `.env`：

```ini
TRANSCODE_CRF=21
TRANSCODE_MAX_HEIGHT=1080
REMOTE_MAX_HEIGHT=2048
REMOTE_BITRATE_KBPS=2800
```

`play_info()` 算出來的遠端上限是 `min(2048, 1080) = 1080`，
而**片庫裡 107 部本來就不高於 1080**。所以實際發生的事情是：

> **解析度幾乎沒降，位元率砍到 2.8 Mbps。** 原檔平均 10 Mbps，
> 也就是砍到約 28%，而畫面大小一樣 —— 這正是「模糊、動態場面糊成塊」的定義。

而且 `-maxrate 2800k -bufsize 5600k` 是硬上限，會直接壓過 `-crf 21`：
CRF 想給的位元率被 VBV 砍掉，CRF 這個設定在遠端等於沒有作用。

上行 100 Mbps 的情況下這個上限沒有存在的理由。**本輪已改成**：

```ini
REMOTE_MAX_HEIGHT=2160      # 實質不縮放（修好 falsy-0 之後填 0 也真的是不限）
REMOTE_BITRATE_KBPS=12000   # 天花板，不是目標；只擋高動態瞬間爆量
NVENC_CQ=28                 # 新增。硬體編碼自己的一把尺，見量測結果 v3
HDR_TONEMAP_ALGO=hable      # 從 mobius 改回來；bt2390 是無效值，見「其他較小的」
```

> **這幾行在 v4／v5 之後還要再動一次**：`REMOTE_BITRATE_KBPS` → 8000、
> `X264_PRESET` → `medium`、`NVENC_CQ` → 25、`TRANSCODE_CRF` → 17（暫定），
> 重編預設改走 NVENC 且碼率導向。見〈量測結果 v5〉的結論表。

**`X264_PRESET` 這一項被翻過兩次，值得記下來為什麼。**
v3 判「維持 `veryfast`」，依據是 SSIM：veryfast 0.9742 對 medium 0.9730，
medium 花更多碼率、分數反而略低。v4 換上帶 libvmaf 的 ffmpeg 重量同一段，
結論相反：**veryfast 91.5 對 medium 93.6**，medium 多花 9% 碼率換到 **+2.1 VMAF**。

差別不在片源也不在參數，在**尺**。SSIM 在這個區間已經飽和，
那 0.0012 的差距是噪音；拿噪音下的結論，方向對錯完全是運氣。
→ **用飽和的指標下的結論等於沒有結論。**

### 第 1.5 層　兩個 falsy-0 的 bug（同一個成因）

**「原畫質」在遠端其實沒有生效。** 前端選「原畫質」送的是 `?h=0`，而 `play_info()` 裡：

```python
chosen_h = h or default_h                                   # h=0 → 回到 default_h
chosen_b = default_b if not h else (0 if h >= ... else ...)  # not 0 為真 → 仍然鎖 2800
```

`0` 是 falsy，於是「不縮放」被當成「沒指定」：解析度回到 1080、位元率仍然鎖在 2800。
**使用者按了畫質選單、看到提示、什麼都沒有改變。** 要用 `h is None` 判斷。

同一個成因還有一處：`settings.remote_max_height or 720` 讓 `REMOTE_MAX_HEIGHT=0`
不是「不限」而是**退回 720**。文件與 UI 都說 0 = 不縮放，實際相反。
`TRANSCODE_MAX_HEIGHT` 的 `or 1080` 同理。

> 這兩個都不是效能或畫質的取捨，是「設定了但沒有作用」——
> 跟 B+ 節點名的最惡毒失效模式是同一種。

### 第 2 層　編碼效率（只在真的必須重編時才有意義）

| 項目 | 現況 | 問題 |
|---|---|---|
| `X264_PRESET` | `veryfast` | 同 CRF 下 preset 越快，要達到同樣觀感需要越高的位元率。**在有 maxrate 上限時，效率差直接變成畫質差** |
| NVENC 參數 | `-preset p4 -rc vbr -cq 21 -b:v 0 -bf 0` | `-bf 0` 關掉 B-frame 是實打實的效率損失；p4 偏快；沒有 `-tune hq`、沒有 `-multipass` |
| `-profile:v high` | 8-bit | 13 部 10-bit 片源會被降到 8-bit → 暗部色帶 |
| `-sc_threshold 0` | 段內不插 I 幀 | 場景切換後幾幀會糊。段首已由 `-force_key_frames` 保證是 I 幀，scenecut 可以開回來 |
| `HDR_TONEMAP_ALGO` | `mobius` | 高光壓得保守、整體偏灰。6 部 HDR 受影響 |

> **這張表寫的是 4.2.3 時代的現況。** 換上 8.1 之後 `p5`／`-tune hq`／`-multipass`
> 都拿得到了（`.env` 的 cq 也已經分家成 `NVENC_CQ=28`），
> 而「x264 與 NVENC 誰好」在 v4 有了答案 —— 以 v4 為準。
> 還沒動的是 `-profile:v high` 的 8-bit 與 `-sc_threshold 0`。

**這一層要用量測決定，不要用猜。** 同一個 CRF 在不同 preset 下畫質**並不相同**，
所以只比 kb/s 會得到反向的結論（實測驗證過：合成片源上 veryfast 的 kb/s 反而更低）。
量測工具 `app/vidprobe.py`（`測試畫質.bat`／`測試畫質-全套.bat`）：
從片子中間取一段，先**無損重編**成參考檔，再用各組設定各編一次，
回報**位元率＋速度＋與參考的 VMAF／SSIM**。
第一列是**對齊自檢**（無損重編，只能是 ~100），第二列刻意就是目前 `.env` 的設定，
最後是**位元率階梯**（ABR 綁住碼率，x264 與 NVENC 各一條曲線）。
參考為什麼要先落地成檔案、自檢為什麼一定要有，見〈量測結果 v4〉的「工具的兩個雷」。

它同時解決「這台機器到底有沒有顯卡」：ffmpeg 列出 `h264_nvenc` 不代表能用
（沒有 NVIDIA 顯卡的機器一樣會列出來），所以每個硬體編碼器都真的編 60 格 1080p，
回報 fps 或失敗原因，並問 `nvidia-smi` 拿型號與驅動版本。

### 量測結果（2026-09-02，實機跑過 `測試畫質.bat`）

> **這一節的兩個結論後來都被 v4 修正了**：ffmpeg 該裝的不是 gyan 的 full build 而是
> **BtbN 的 n8.1**（gyan 現在的 release 是 9.0.1，而 9.0 的 NVENC 在 Pascal 上載不起來），
> 而「Pascal 的 NVENC 畫質不如 x264 medium」在同碼率下**不成立**。
> 環境探測的部分（版本、顯卡、哪些編碼器能用）仍然是有效的紀錄。

| 項目 | 結果 |
|---|---|
| ffmpeg | **4.2.3（2020 年）**，而且路徑是 `C:\Program Files\ImageMagick-7.1.0-Q16-HDRI\ffmpeg.EXE` |
| 顯卡 | **NVIDIA GeForce GTX 1070**，驅動 582.66、8 GB |
| NVENC | `h264_nvenc` 可用（1080p 約 95.6 fps）、`hevc_nvenc` 可用（約 109.5 fps） |
| QSV | 不可用（`Error initializing an internal MFX session: unsupported`） |
| AMF | 不可用（`amfrt64.dll failed to open`） |
| 軟體編碼器 | libx264、libx265、libaom-av1。**沒有 libsvtav1、沒有 libvmaf** |

這兩行把第 2 層的結論整個改寫：

**1. `FFMPEG_PATH=ffmpeg` 解到了 ImageMagick 附帶的那一份。**
那種附屬版本不會有人更新，也常常少編譯選項。而 4.2 的影響是具體的：
NVENC 的 `p1`~`p7` preset、`-tune hq`、`-multipass` **全部是 ffmpeg 5.0 之後才有的**。
也就是說 `media.py` 的 nvenc tier 裡那個 `p4` 在這台機器上永遠選不到，
會退到 `medium`；`-tune hq` 與 multipass 更是連試都試不了。
**現在拿不到 NVENC 的畫質上限，不是因為顯卡，是因為 ffmpeg 太舊。**
順帶的：沒有 libvmaf 所以只能用 SSIM 評分，沒有 libsvtav1 所以 AV1 只剩下慢到不能用的 libaom。

→ 換一個獨立的新版 ffmpeg（Windows 上 gyan.dev 的 full build 有 libvmaf 與 libsvtav1），
並在 `.env` 用**完整路徑**指定 `FFMPEG_PATH`，不要靠 PATH 去猜。
這是這一節投報率最高的一步，而且零風險。

**2. GTX 1070 是 Pascal 世代的 NVENC。** 它很快（1080p 95 fps，足以即時服務好幾個人），
但同位元率的畫質明顯不如 Turing（RTX 20）之後的世代。所以對「必須重新編碼」的那 13 部，
**CPU 的 x264 medium 很可能比 NVENC 好看**；NVENC 的價值在多人同時觀看時的吞吐。
消費卡另外有並行編碼工作階段的上限（依驅動版本大約 2～5 條），多人同時轉碼會撞到。

→ 正確的用法是分工：畫質優先用 x264（`medium`），併發優先用 NVENC。
先升級 ffmpeg，再用 `測試畫質.bat` 對一部真的片子跑一次，用 VMAF 決定門檻在哪。

> 工具本身的一個小教訓：`測試畫質.bat` 的註解一律寫 ASCII。cmd.exe 是用
> **當下的主機碼頁**逐行解析批次檔的，UTF-8 的中文註解會被誤解碼、
> 然後解析器會把亂碼當成命令去執行（實際發生過，四行 `REM` 變成四個
> 「不是內部或外部命令」）。中文全部放在 Python 那一側。

### 量測結果 v2（同日，拿一部 4K HDR 片源實測）

> **這一節與 v3 的分數只有 SSIM，而且 4K 那幾組後來證實是無效的。**
> 保留是因為推導過程（上限在砍畫質、4K 是算力問題）仍然成立；
> **凡是牽涉「哪個設定畫質比較好」的結論，一律以 v4 為準。**

片源：`Pinocchio.Unstrung.2026.MULTi.2160p.UHD.BluRay.DV.HDR.HEVC.AC3.mkv`——
3840×2160、hevc、10-bit、`smpte2084`（HDR10）、9,655 kbps、82 分鐘。

| 設定（CRF 21、30 秒取樣） | 位元率 | 速度 | SSIM |
|---|---|---|---|
| 現況：veryfast ＋ 上限 2800k | 2,421 kbps | **0.93x** | 0.9986 |
| medium ＋ 上限 2800k | 2,886 kbps | 0.41x | 0.9987 |
| veryfast，不設上限 | 3,873 kbps | 0.55x | 0.9988 |
| medium，不設上限 | 5,359 kbps | 0.42x | 0.9989 |
| NVENC（兩組） | — | — | **失敗**（見 G-6） |

三個結論：

**1. 上限確實在砍畫質。** 同一段、同一個 CRF，不設上限的 veryfast 要 3,873 kbps，
被 2800k 一壓變成 2,421 kbps —— 少掉的 37% 就是被丟掉的細節。medium 更明顯：
5,359 → 2,886，幾乎砍半。

**2. 4K HDR 的問題不是模糊，是追不上。** 現況那組只有 **0.93x 即時** ——
比播放速度還慢，等於播到哪裡就轉到哪裡、隨時可能斷；而 `PREFETCH_MIN_SPEED=1.5`
會讓預轉直接停掉，所以連緩衝都沒有。medium 只有 0.41x，完全不能用在即時串流。

> 這一項與位元率無關，是**算力**。而 `.env` 裡 `FFMPEG_DECODE_HWACCEL=none`——
> 4K HEVC 10-bit 在 CPU 上解碼是整條管線最貴的一段，而 GTX 1070 的 NVDEC
> **支援 HEVC Main10 硬體解碼**。解碼與編碼是不同的硬體單元，
> `FFMPEG_DECODE_HWACCEL=cuda` 解不了的片源會自動退回 CPU，風險低。
> 這是 4K 這一類片源最該先開的一項。

（注意：這批數字是拿**原尺寸 4K** 直接重編量到的，而生產環境會先縮到 1080 再編，
所以實際速度會比 0.93x 好一些。量測工具已改成走 `media.build_video_filters()`
同一條濾鏡鏈（含 tonemap），升級 ffmpeg 之後要再量一次才是可用的基準。）

**3. SSIM 的分辨力不夠。** 四組全部落在 0.9986–0.9989，差 0.0003，
而肉眼差異明顯 —— SSIM 在高畫質區間會飽和。**要判斷「開到多少就夠」必須用 VMAF**，
而 libvmaf 要新版 ffmpeg 才有。這是升級 ffmpeg 的第三個理由。

### 量測結果 v3（帶 remux pre-flight 的完整一輪）

> 同上：Direct Stream 的可行性結論（keyframe、時間戳）v4 再次確認，仍然有效；
> **畫質高低的結論以 v4 為準。**

兩部片：`Dark.Matter.2024.S01E02`（1080p h264+eac3、10,891 kbps、1920×960）
代表片庫裡的 97 部；4K HDR 那部是最壞情況。

**1. Direct Stream 是綠燈。** 這是本輪最重要的結果：

| 檢查 | 結果 |
|---|---|
| keyframe 間距 | 最短 1.38s、**中位 3.63s**、最長 3.96s |
| 可對齊 6 秒分段 | **是**（最長間距 < 分段長度） |
| 試切 `-c:v copy -c:a aac` | 成功，0.35 秒產出 6 秒段 |
| 時間戳警告 | **零** |

所以第 0 層的實作可以簡化：照 keyframe 切就能對齊，
不必上 fMP4 + byte-range 那條複雜路線。**而那組 keyframe 邊界後來變成兩階 HLS
的核心**：上階只能照它切，下階就跟著它切，兩階的邊界因此天生一致（見第 0 層）。順帶量到峰值：
6 秒段 15.4 MB ≈ **20 Mbps 峰值**（平均 10.9），
direct stream 的頻寬規劃要按峰值算，不是平均。

**2. NVENC 的 `-cq` 不是 x264 的 `-crf`。**

| 設定（1080p、60 秒取樣） | 位元率 | 速度 | SSIM |
|---|---|---|---|
| x264 veryfast ＋ 上限 2800k | 2,297 kbps | 6.55x | 0.9736 |
| x264 medium ＋ 上限 2800k | 2,698 kbps | 3.34x | 0.9729 |
| x264 veryfast，不設上限 | 3,238 kbps | 6.29x | 0.9742 |
| x264 medium，不設上限 | 3,556 kbps | 3.26x | 0.9730 |
| **NVENC `-cq 21`（修好 G-6 之後真的跑起來了）** | **10,195 kbps** | 17.31x | 0.9767 |
| NVENC 調滿（slow／vbr_hq／bf 3／2pass／lookahead／AQ） | 10,458 kbps | 11.62x | 0.9760 |

> NVENC 分數最高，但它**花了 10.2 Mbps** —— 幾乎等於原檔的 10.9 Mbps，
> 也就是幾乎沒有壓縮。x264 用 3.2 Mbps 拿到 0.9742，NVENC 用三倍碼率
> 換到 +0.0025。**那不是效率，是花錢買的。**

規格結論：**`TRANSCODE_CRF` 一個數字不能同時服務兩種編碼器。**
`-cq 21` 在 NVENC 上等於「幾乎不壓縮」。NVENC 路徑要嘛用碼率上限
（`-b:v`／`-maxrate`），要嘛把 cq 往上調（大致 28–32 才對得上 x264 crf 21 的區間）。
量測工具已新增「NVENC 同碼率對照」，下一輪就能直接看同碼率下誰好。

**3. `FFMPEG_DECODE_HWACCEL=cuda` 這條建議撤回（暫時）。**

實測：1080p 11.62x → **9.73x**、4K 0.44x → **0.34x** —— 開了硬體解碼**更慢**。
原因是混合模式：`-hwaccel cuda` 沒有搭 `-hwaccel_output_format cuda` 時，
GPU 解出來的畫面要下載到系統記憶體給 CPU 濾鏡（scale／zscale tonemap），
再上傳回 GPU 編碼 —— **每一幀過兩次 PCIe**。要讓整條鏈留在 GPU 需要
`scale_cuda` 加 GPU 端 tonemap，而 **ffmpeg 4.2 沒有 GPU tonemap**。

→ 硬體解碼不是「先開就對」，它跟升級 ffmpeg 綁在一起。不需要 tonemap 的片源
可以先開全 GPU 鏈，工具已加了那一組對照。

**4. 4K 那一輪的數字無效，原因值得記下來。**

六組全部量到 24–26 kbps、SSIM 1.0000、0.44x —— 這是「片段解不出畫面」的指紋。
根因就在 remux 試切的警告裡：

```
Invalid DTS: -873900 PTS: -877680 in output stream 0:0, replacing by guess
Non-monotonous DTS in output stream 0:0; previous: -877589, current: -881370
```

**那部帶 Dolby Vision 的 4K mkv 時間戳是負的。** 工具原本先用 `-c copy`
切一段當參考，那個片段解不出畫面，於是每組都「編了一個空的」，
比對時參考也是同一個空片段，所以 SSIM 完美。工具已改成**直接從原檔取樣**，
並在位元率低到不合理時標成「數字無效」而不是給一個假分數。

這個雷同時是第 0 層的結論之一：**這部片連 remux 都不能用**
（試切就噴了三行時間戳警告），只能重編 —— 而重編又同時撞上 tonemap 與速度。
4K HDR ＋ DV 是最難的個案，要單獨處理。

**5. 1080p 完全不需要 GPU。** CPU veryfast 6.55x、medium 3.34x，
同時服務好幾個 1080p 轉碼都有餘裕。GPU 的位置是**併發**與**4K**，
不是「所有轉碼都丟給它」。

### 量測結果 v4（2026-09-03，換上 ffmpeg 8.1 ＋ VMAF 的完整一輪）

這一輪回答了 v2／v3 答不出來的兩個問題。前面三輪只有 SSIM，
而 SSIM 在高畫質區間會飽和 —— **「12 Mbps 夠不夠」這種問題它答不了**。

#### 換哪一版 ffmpeg：**8.1，不是 9.0**

先裝 9.0，NVENC 整組載不起來：

```
Driver does not support the required nvenc API version. Required: 13.1 Found: 13.0
```

不是裝錯，是**這張卡永久不相容**：

1. nv-codec-headers 的 master 對應 Video Codec SDK **13.1.15**，README 明寫最低驅動 **610.0**。
2. ffmpeg **9.0／master 就是拿這份標頭編的**，所以執行時要求 API 13.1。
3. **R580 是 NVIDIA 給 Maxwell／Pascal／Volta 的最後一個驅動分支。**
   這台是 582.66，已經在那個分支裡 —— **610 對 GTX 1070 永遠不會出現。**

而 BtbN 的 build script **每個 ffmpeg 分支釘不同的標頭版本**
（`scripts.d/50-ffnvcodec.sh`）：8.0／8.1 用 SDK **13.0**（要驅動 570 以上），
9.0 與 master 用 13.1。所以退到 **n8.1** 就能用，而且 libvmaf、libsvtav1、
`p1`~`p7`、`-tune hq`、`-multipass` **一個都沒有少** —— 那些全是 5.0 之後的東西。

| 決定 | 值 |
|---|---|
| build | BtbN `ffmpeg-n8.1-latest-win64-gpl-8.1.zip`（.zip，Windows 內建 `curl`＋`tar` 就能裝） |
| 實裝版本 | `n8.1.2-50-g1a748fe2cd-20260902` |
| 位置 | `C:\Users\Administrator\ffmpeg\bin\`（`C:\ffmpeg` 未提權建不了，UAC） |
| `.env` | `FFMPEG_PATH` / `FFPROBE_PATH` 填**完整路徑**，不加引號（雙引號值會被 dotenv 處理轉義，反斜線會壞） |

> **不要只用 `-encoders` 判斷硬體編碼器能不能用。** `av1_nvenc` 列得出來但
> 「No capable devices found」—— AV1 硬體編碼要 Ada（RTX 40）才有。
> 工具每個編碼器都真的編 60 格才回報，這一輪也因此第一時間看到 API 版本的問題。

**G-6 的 regex 在 8.1 上確認仍然有效**：`app/media.py` 自己的解析器挑到
`preset: p5　rc: vbr　tune: hq　multipass: fullres`。報告現在會固定印這一行。

#### 工具的兩個雷：分數可以「看起來只是偏低」而其實全錯

v4 的第一次結果整批是廢的，而且**不會報錯、不會爆掉**。發現它靠的是一個
內容無關的檢查：**把片段用 `-qp 0` 無損重編，再用同一套方法評分 —— 只能是 100。**

量到 **17.2**。

| 做法 | 無損重編應得 100 | CRF 21 |
|---|---|---|
| 比對時才 seek 參考 | **22.4** | 22.4 |
| 參考落地成 `.mkv`、變體是 `.mp4` | **72.0** | — |
| 參考落地成 `.mp4`、變體也是 `.mp4` | **99.99** | 91.2 |

**第一層：比對時 seek 參考會多一格。** `-ss` 落在兩格中間時解碼端會把第一格
複製一份再往下吐，參考變成 `[F0, F0, F1, F2…]` 而變體是 `[F0, F1, F2…]` ——
整段錯開一格，**每一格都在跟前一格比**。（把兩邊前六格算 md5 就看得到重複。）
這個雷是 v3 修 4K DV 的 DTS 問題時自己種下的：把「先 `-c copy` 切一段當參考」
改成「參考直接從原檔取樣」，DTS 問題沒了，換來一個更難發現的錯。

**第二層：時基。** 參考落地成檔案之後**還是 72 分**，而那兩個檔案逐格 md5 完全相同、
格數也一樣。原因是 matroska 把時間戳四捨五入到毫秒（0.042、0.083…），
mp4 存的是精確的 1/24（0.041667、0.083333…），而 **`libvmaf` 是按時間戳配對影格的**，
累積的捨入誤差會讓它配錯格。

**正解**：參考先用**同一條命令、同一條濾鏡鏈**解碼後無損重編成 `.mp4`
（重編過所以沒有 DTS 問題，無損所以畫素不變，同容器所以時基一致），
之後每個變體都跟這個檔案比，兩邊都不 seek。60 秒 1080p 的參考檔約 300MB～1GB，
跟著暫存目錄一起刪。

**而且工具現在每一輪都自己驗一次**：變體清單第一列固定是「對齊自檢」，
沒過就印一段很大聲的警告叫你不要用底下任何數字。

> 這一類錯的特徵值得單獨記住：**分數不會爆掉，只會一路偏低而且對位元率幾乎沒反應**
> （2.8→12 Mbps 只動 1.0 分）。它看起來就像「這個編碼器就是爛」。
> 跟 FTP 那支工具量到「每條連線都剛好 0.75 MB/s」是同一種失效 ——
> **假數字看起來像真數字**，只能靠一個「已知答案」的檢查去接住。

#### 結論 (a)：x264 與 NVENC 各該用在什麼情況

**同碼率下 NVENC 在每一級都贏 x264 `veryfast`**，而且快 1.5 倍。
換個講法最有感：

> **NVENC 在 2800k 拿到 92.3；x264 `veryfast` 要花到 6000k 才追平（92.7）。**
> 同樣的畫質，碼率差一倍以上。

唯一追得上 NVENC 的 CPU 設定是 `medium`（3,475 kbps／93.6，對 NVENC 同碼率約 93.2），
但它只有 3.14x —— NVENC 的三分之一。

| 情況 | 用哪個 | 為什麼 |
|---|---|---|
| 必須重編（預設） | **NVENC** | 同碼率畫質最好，且 8～9x 即時，一張卡撐得住多人 |
| NVENC 撞到並行上限或失敗 | **x264 `medium`** | 同碼率追得上 NVENC；3.14x 對 1080p 仍然夠 |
| ~~x264 `veryfast`~~ | **不要當預設** | 同碼率下輸給另外兩個，省下來的 CPU 買不到對應的畫質 |

消費卡有並行編碼工作階段上限（依驅動版本約 2～5 條），所以 **x264 這條路要留著**，
它是退路不是首選。

#### 結論 (b)：`REMOTE_BITRATE_KBPS` 開到多少就夠

先講一個比數字更重要的發現：**現在這個上限根本咬不到。**
CRF 21 在片源 A 上只吐 3,174 kbps —— 「上限 12000k」與「不設上限」兩組的
位元率與分數**完全相同**。所以現在限制畫質的不是上限，是 **CRF**。

分兩類看：

| 片源 | 答案 |
|---|---|
| 可以 remux 的 97 部 | **上限對它們沒有意義。** 走 Direct Stream 畫質等於原檔。對照組很清楚：重編到 11.6 Mbps 只有 VMAF 94.6，而 remux 用 10.9 Mbps 是無損 —— **花更多頻寬換更差的畫質** |
| 必須重編的（4K/HEVC → 1080p） | VMAF 到 95：NVENC **2800k**、x264 **4000k**；邊際增益掉到 0.5 以下：兩者都在 **8000k** |

→ **`REMOTE_BITRATE_KBPS` 設 8000。** 那是曲線轉折的地方；再往上加碼率買不到畫質
（8000→12000 只有 +0.3～+0.4）。12000 留著也無害，因為它咬不到 —— 但把它寫成 8000
才誠實地表達「這是天花板，而天花板在這裡」。

**真正該調的是 `TRANSCODE_CRF`。** 它在片源 B 上只吐 1,093 kbps／VMAF 92.2，
而同一個片源綁 2800k 就有 94.6 —— **CRF 21 太保守，把該花的碼率省掉了。**
該調到多少**這一輪沒有量**，不猜；見下面的待辦。

#### 這一輪沒有回答的（不要當成已知）

| 待辦 | 為什麼要量 |
|---|---|
| ~~**CRF／cq 階梯**~~ | **已完成，見 v5。** `NVENC_CQ=25`、`TRANSCODE_CRF=17`（暫定，preset 換 medium 後要再確認） |
| **NVENC 的 spatial-AQ** | 異常：cq 28 下「調滿」花 3,305 kbps 拿到 92.8，「現況」花 2,579 kbps 拿到 94.0 —— 更多碼率更低分。最可能是 `-spatial-aq` 把位元重分配到平坦區（AQ 常壓低 VMAF 但主觀較好）。**綁碼率的階梯不受影響**，但這代表 NVENC 該走碼率導向而不是 cq 導向 |
| **libplacebo GPU tonemap** | 4K 仍然是**算力**問題不是碼率問題：x264 1.15x、NVENC 1.37x，兩個都低於 `PREFETCH_MIN_SPEED=1.5`，預轉根本不會啟動。瓶頸在 4K HEVC 10-bit 的 CPU 解碼 ＋ zscale tonemap。8.1 帶了 **libplacebo**，這是決策 12 翻案的前提 |

> CUDA 全 GPU 那組在 1080p 只從 8.92x 到 9.08x，是雜訊。它只在不需要 tonemap 時才會被測到，
> 而不需要 tonemap 的片源本來就該 remux —— 所以它現在沒有用武之地。

| x264 `veryfast` CRF 17 | 11,763 | 94.7 | 2,231 | 94.5 |
| x264 `veryfast` CRF 15 | 17,800 | **95.9** | 3,182 | **95.4** |
| NVENC cq 31 | 1,856 | 91.1 | 1,218 | 93.2 |
| NVENC cq 28 | 3,305 | 92.8 | 1,931 | 94.6 |
| NVENC cq 25 | 5,613 | 93.9 | 3,185 | **95.6** |
| NVENC cq 22 | 9,026 | 94.9 | 4,938 | 96.3 |

速度全程平穩（A：x264 5.5～6.2x、NVENC 8.5～9.2x；B：x264 1.1x、NVENC 1.3x），
**旋鈕不影響速度** —— 這是 CRF 這類旋鈕跟 preset 的差別。

#### 先看一個交叉驗證

品質階梯與位元率階梯是兩條**互相獨立**的路徑（一邊綁碼率、一邊綁品質），
在碼率相近的點上分數應該吻合：

| 品質階梯 | 位元率階梯 | 差 |
|---|---|---|
| A x264 CRF 17：11,763 kbps／94.7 | A x264 12000k：11,646 kbps／94.6 | −0.1 |
| B x264 CRF 15：3,182 kbps／95.4 | B x264 4000k：3,572 kbps／95.3 | −0.1 |
| B NVENC cq 25：3,185 kbps／95.6 | B NVENC 4000k：3,930 kbps／96.0 | +0.4 |

**兩種方法在同一個碼率上量到同一個分數。** 這是「量測本身可信」最強的一種證據 ——
比自檢更強，因為自檢只證明對齊，這個證明整條管線的一致性。

#### 最重要的一項：片源 A 重編不到 VMAF 95

看 A 那一欄：**要到 VMAF 95 得花 17.8 Mbps（x264 CRF 15），而原檔只有 10.9 Mbps。**
NVENC 好一些但 cq 22 花了 9 Mbps 也只有 94.9。

> **這 97 部片重編到「看不出差異」比原檔還貴。** 不是貴一點，是貴 60%。
> 第 0 層的結論到這裡從「應該不要重編」變成「**重編這條路在數學上就不成立**」——
> Direct Stream 不是比較好的選項，是唯一能拿到透明畫質的選項。

而片源 B（真的必須重編的那一類）便宜得多：縮到 1080p 之後
**x264 CRF 15 花 3,182 kbps、NVENC cq 25 花 3,185 kbps，兩個都到 95**。
同樣的碼率、同樣的分數 —— 這一類的 95 分大約就是 3.2 Mbps。

#### 結論：`.env` 該填什麼

| 設定 | 從 | 到 | 依據 |
|---|---|---|---|
| `X264_PRESET` | `veryfast` | **`medium`** | 同 CRF 下 +2.1 VMAF，只多花 9% 碼率（v4） |
| `REMOTE_BITRATE_KBPS` | 12000 | **8000** | 曲線轉折點；8000→12000 只有 +0.3～+0.4（v4） |
| `NVENC_CQ` | 28 | **25** | B 到 95.6／3,185 kbps、A 到 93.9／5,613 kbps，兩邊都在上限之內 |
| `TRANSCODE_CRF` | 21 | **17（暫定）** | 見下面的說明 |

**`TRANSCODE_CRF` 為什麼是暫定的。** 這一輪的 x264 曲線是用 `veryfast` 量的
（因為 `.env` 還沒改）。CRF 15 才到 95，但那要 17.8 Mbps —— 而上限 8000 會把它切掉，
等於設了不生效。**preset 與 CRF 會互相影響**：v4 量到同一個 CRF 下 medium 比 veryfast
多 2.1 分，所以 preset 換成 `medium` 之後，17 很可能就到 95 了。

CRF 17 的依據是「veryfast 下 A 94.7／B 94.5，換 medium 只會更好」——
這是有基礎的推論，不是量到的數字。要確定就把 `X264_PRESET` 改成 `medium` 之後
重跑一次 `測試畫質-CRF.bat`（約 25 分鐘）。**因為 NVENC 是預設路徑、x264 只是退路，
這一項的精確值優先度不高。**

> 另外注意：改完之後 A 這一類**應該根本不會走到編碼器**（走 remux）。
> CRF 與上限真正服務的是必須重編的那 13 部，以及 remux 失敗時的退路。

### 免費租用顯卡：不採用，而且它解決不了這個問題

**GPU 換來的是速度，不是畫質 —— 這個通則在這台機器上被實測推翻了一半，見 v4。**
通則說：同位元率下 NVENC 的 H.264 一般不會超過 x264 的慢速 preset。
實測說：**同碼率下這張 1070 的 NVENC 在每一級都贏 x264 `veryfast`**（+0.8～+1.8 VMAF），
只有 x264 `medium` 追得上，而 medium 只有 NVENC 三分之一的速度。
通則沒有錯，錯在拿它跟「生產環境實際在用的 preset」比 —— 那不是慢速 preset。

免費 GPU 平台不能拿來做這件事，理由不是效能：

| 平台 | 為什麼不行 |
|---|---|
| Google Colab | 使用條款**明文禁止**「file hosting, media serving, or other web service offerings not related to interactive compute」。免費層另外會因為「bypassing the notebook UI」與閒置而隨時終止，執行時間上限 12 小時 |
| Kaggle / HF ZeroGPU / Lightning 之類 | 都是給互動式 ML 工作的短時額度，同樣不是常駐服務，也同樣不允許當媒體服務 |
| 按時計費的 RunPod／Vast.ai | 技術上可行、也不貴，但**片源在你家的 FTP** |

最後那一項是所有雲端 GPU 的共同硬牆：即時轉碼要求片源與編碼器在同一台機器上。
要讓雲端 GPU 轉，得先把幾十 GB 上傳，轉完再串回來 —— 流量與延遲都是雙倍，
而你原本的問題就是遠端頻寬。離線批次預轉（把整個片庫先轉成瀏覽器友善格式）
在技術上成立，但同樣要上傳整個片庫，而且那還是「重新編碼」，
與第 0 層的結論（**不要重編**）直接矛盾。

**結論：只有這台機器上的 GPU 有意義，而且只對真的必須重編的那 13 部有意義。**
這台有 GTX 1070（Pascal）。換上 ffmpeg 8.1 之後 `p6`／`-tune hq`／`-multipass` 都拿得到，
同碼率的畫質贏過生產在用的 x264 `veryfast`，速度也快 1.5 倍 —— 見 v4。

### 運維：Cloudflare 要怎麼設，畫質與區網登入才都成立

這兩件事看起來無關，其實是同一個問題的兩面：**TLS 在哪裡結束。**

#### 政策的正確引用（修正）

先修正前一版的引用。**Section 2.8 已經在 2023 年退場**，
Cloudflare 把限制搬進 **CDN 的 Service-Specific Terms**。
限制的實質沒變：**自架的影片與大檔不能透過 CDN 交付**，
除非內容託管在 Cloudflare 自己的服務（Stream／Images／R2）上。

差別在於它現在只綁 CDN 這個產品，不再是罩住所有服務的傘狀條款 ——
所以 **Zero Trust／WARP 的私有網路路由不在這條限制裡**，那不是 CDN。
這一點正好給了下面的做法一個乾淨的依據。

#### 兩條路，選一條

| | **A. 區網 IP 直連（今天就能用）** | **B. 區網也給真憑證（安全不打折）** |
|---|---|---|
| 區網怎麼連 | `http://192.168.3.222:29880` | `https://lan.longhopick.com:29880` |
| `COOKIE_SECURE` | 必須 `false` | **維持 `true`** |
| 要做的事 | 改一行 `.env` | Cloudflare 加一筆 grey-cloud A 紀錄 ＋ 用 DNS-01 申請憑證 ＋ 自動續期 |
| 殘留風險 | session cookie 在區網是明文，同網段的人嗅探得到 | 無 |
| 適合 | 只有自己家、想先動起來 | 想長期就這樣用 |

**A 的補償設定**（在 Cloudflare 做，補回應用層不再送的 HSTS）：

1. **SSL/TLS → Edge Certificates → Always Use HTTPS：開。**
2. 同一頁 **HSTS：開**，Max Age 先選 6 個月，
   `includeSubDomains` 與 `Preload` **先不要開**。
3. 確認 **SSL/TLS 模式是 Full (strict)** —— Flexible 會讓 Cloudflare 到自家之間是明文。

> **HSTS 的 `includeSubDomains` 是這裡最容易自傷的一格。**
> 一旦對 `longhopick.com` 開了它，任何走 **plain http 的子網域都會被瀏覽器強制轉 https**
> —— 包含將來想拿來給區網用的 `lan.longhopick.com`。
> 而 **HSTS 對純 IP 位址無效**，所以 `http://192.168.3.222:29880` 不受影響。
> 換句話說：走 A 的話用 IP，**不要**給區網取主機名。

**B 的做法**（一次設好，之後全自動）：

1. Cloudflare DNS 加一筆 `lan.longhopick.com` → `192.168.3.222`，
   **代理必須先關掉再填 IP**（填了私有 IP 之後開關會顯示 `DNS only - reserved IP`，
   但要先手動關代理才存得起來）。私有 IP 是公開可查的，但它只洩漏「內網用 192.168.3 網段」。
   > 不想公開這筆紀錄也可以完全不加，改在筆電的 `/etc/hosts` 或路由器 DNS 指過去 ——
   > **憑證用的是 DNS-01，只需要 TXT 紀錄，跟 A 紀錄無關。**
2. 開一個 **範圍只有 `Zone / DNS / Edit`** 的 API token，拿它跑 DNS-01
   （Windows 上用 win-acme，選 Cloudflare 的 DNS validation plugin），
   憑證簽給 `lan.longhopick.com`。
   > 一定要用 **DNS-01** 而不是 HTTP-01：HTTP-01 需要 Let's Encrypt 從外面連到 80 埠，
   > 而這個名字指向私有 IP，外面連不到。
3. uvicorn 直接吃憑證（`--ssl-certfile` / `--ssl-keyfile`），或前面擺 Caddy／nginx 收 443。
4. `COOKIE_SECURE=true` 維持不動，HSTS 這時可以放心全開。
5. win-acme 的續期排程要驗過一次 —— 憑證 90 天到期，續期失敗會變成「某天突然登不進去」。

#### 影片流量：走 WARP 私有網路，不要走橘雲

不管選 A 還是 B，**遠端看片都不該經過 `video.longhopick.com` 的橘雲代理** ——
那是 CDN，就是上面那條限制管的東西。把位元率從 2.8 開到 12 Mbps 卻不換路徑，
等於把違規流量放大四倍。

做法（沿用現有的 cloudflared，不用開任何對外埠）：

1. Zero Trust → **Networking → Routes → Create route → Tunnel CIDR**，
   選現有的 tunnel，填 `192.168.3.0/24`。
2. 每台要看片的裝置裝 **WARP** 並登入同一個 Zero Trust 組織。
3. **改 Split Tunnel** —— 這一步不做就一定不通：
   WARP 預設**排除**所有 RFC 1918 網段。Exclude 模式要把
   `192.168.0.0/16` 那條刪掉，再把自己沒用到的部分補回去
   （Cloudflare 文件附了 CIDR 計算機）；Include 模式則直接把 `192.168.3.0/24` 加進去。
4. Traffic policies → Traffic settings → 開 **Allow Secure Web Gateway to proxy traffic**（TCP＋UDP）。
5. 之後在外面直接用 `192.168.3.222:29880`，跟在家一樣。
6. `video.longhopick.com` 留著給控制介面，以及「臨時在別人的裝置上要看一下」的退路。

**這一步做完必須配套改一行 `.env`**：

```
LOCAL_NETWORKS=100.64.0.0/10
```

理由在 `auth.py` 的註解裡已經寫了：**WARP／Tailscale 的 CGNAT 網段 `100.64.0.0/10`
在 Python 眼中不是 private**，`is_local_network()` 會把它判成遠端，
於是自動套用遠端的降畫質規則 —— 明明是私有隧道，畫質卻被砍。
（`192.168.3.0/24` 本來就被 `is_private` 認出來，寫不寫都一樣。）

#### 順序

1. `COOKIE_SECURE=false` ＋ Cloudflare 開 Always Use HTTPS / HSTS（不勾 includeSubDomains）→ 今天就能用。
2. WARP private network ＋ `LOCAL_NETWORKS=100.64.0.0/10` → 遠端畫質解鎖，且不再踩 CDN 條款。
3. 想把第 1 步的明文 cookie 也收掉，再做 B（`lan.longhopick.com` ＋ DNS-01），
   然後把 `COOKIE_SECURE` 改回 `true`、HSTS 全開。

### 驗收

- 兩階 HLS 的驗收條件寫在第 0 層（那一節的清單比這裡完整）。
- 選「原畫質」之後 profile key 裡的 `b` 是 `0`，而且 `quality.bitrate_kbps` 不再是 2800。

  這一項不是形式，v4 的第一次結果就是整批廢掉的（見「工具的兩個雷」）。
