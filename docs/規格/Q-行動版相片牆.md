## Q. 行動版相片牆：相簿抽屜與檢視切換（**已實作**）

### 這一章要解決什麼

使用者的原話是一句：**「手機裝置看相本的時候沒有看到瀑布流的按鈕。」**

聽起來像「某個 media query 把按鈕藏起來了」。**不是。** 全檔沒有任何規則碰過
`.pmode` 或 `.album-bar`，按鈕從來沒有被 `display:none`。這是一個**版面**問題，
而且症狀與根因不在同一個地方 —— 這一章大半的價值在 Q-0 的量測，不在修法。

---

### Q-0. 現況（先量，不要猜）

在 375×812（iPhone 12/13/14 的邏輯解析度）載入實際的 `style.css` 量測：

| 量測項 | 實測值 |
|---|---|
| `.album-bar` 三個子元素要求的總寬 | **473px**（輸入框 267 ＋ 排序 70 ＋ `.pmode` 116 ＋ gap 20） |
| 該處實際可用的內容寬 | **347px**（375 − `main` 左右各 14 的 padding） |
| → 於是 | `.pmode` **被擠到第三列** |
| `#folderBar`（相簿標籤列）高度 | **7,734px ＝ 9.5 個螢幕** |
| 相片格線真正開始的 y | **7,909px** |
| sticky `header` 高度 | **209px ＝ 視窗的 26%**（換行成約 4 列） |

資料庫實測（`SELECT COUNT(DISTINCT folder) FROM photo WHERE probe_state='ok'`）：

| 項目 | 值 |
|---|---|
| 相簿數 | **141**（全部都有封面縮圖） |
| 相片數 | 21,084 |
| 相簿名末層長度 | 中位數 **18** 字、平均 16.5、最長 **71** 字 |
| 名字超過 12 字的相簿 | **107 / 141** |
| 375px 下每列擠得下幾個標籤 | **138 列裡有 135 列只有 1 個**（`.fchip` 限寬 260px） |

所以「看不到瀑布流按鈕」是**兩件事的合成**：

1. `.pmode` 掉到第三列，看起來像「兩顆沒有標籤的藥丸」而不是一組切換 —— 次要。
2. **7,734px 的標籤列把工具列與相片一起推出視野** —— 主因。標籤列比它導覽的
   內容還長 9.5 倍，那已經不是導覽了。

#### 為什麼這個假設會留在程式裡

`index.html` 原本的註解寫著「**相簿只有十幾個**而且全在同一層，所以維持封面標籤」。
實際是 141 個 —— **錯一個數量級**，而這句話正是「標籤攤平沒問題」這個結論的來源。
`app.js` 的 `goTop()` 裡另有一句「110 個標籤、高 2,974px」，同樣過期。

> **兩條註解都是主動誤導**（不是單純沒更新）：它們給出一個具體數字，讓後來的人
> 不必自己量就相信「規模很小」。所以 Q-4d 把它們一起改掉，寫上量到的值與量法。

### Q-1. 檢視切換找不到（表面症狀）

**決定：不對 `.album-bar` 做 sticky。**

理由：`header` 已經是 `position:sticky;top:0` 且行動版 209px。再疊一條 sticky
`.album-bar`（95px）會**永久佔用 304px，超過視窗的三分之一** —— 為一顆切換鈕付掉
三分之一螢幕不成比例。而且 sticky 需要正確的 `top`，那個值取決於**會隨換行數變動的**
header 高度；`.tree-pane{position:sticky;top:74px}` 已經踩過這個坑（那 74px 在行動版
本來就失準，只因 900px 的 media query 把它改成 `position:static` 才沒有暴露）。

**決定：靠 Q-2 的抽屜把 `.album-bar` 抬進第一屏，另外重排 ＋ 窄版只留圖示。**

- `≤900px`：篩選框吃掉整列（`flex:1 1 100%`），排序與 `.pmode` 併成第二列
  （`.pmode{margin-left:auto}` 靠右，跟排序分邊）。三個各自換行才是症狀的來源。
- `≤560px`：藏掉中文、只留內嵌 SVG 圖示。**先例是同一個斷點下的 `.to-top`** ——
  「文字佔掉的寬度比它提供的資訊值錢」。

圖示用**內嵌 SVG** 而不是文字符號（`▦`/`▥`）：後者在 Windows 中文字體下兩個長得像。
SVG 用 `fill:currentColor`，跟著既有的三個狀態（預設／hover／`.on`）走，不必另寫顏色規則。

> **接受的代價**：`≤560px` 只有圖示，第一次使用的人得靠 `title`（觸控裝置幾乎不會
> 觸發）。中文移到 `aria-label`，所以**報讀器在兩種寬度下讀到的完全一樣**。
> 兩顆並排且一顆永遠是選中態，「這是一組切換」的訊號還在。

#### 踩到的坑：CSS 順序，不是權重

第一版把 `.pmode button svg{display:block}` 寫進檔案下方那個
`@media(max-width:560px)` 區塊（`.to-top` 那一組旁邊），結果**按鈕變成兩顆空白方塊**：
文字被藏了、圖示也沒出現。

原因是 `.pmode` 那一組規則在檔案裡排在 `.to-top` **後面**，於是基準的
`.pmode button svg{display:none}`（第 443 行）出現在 media query（第 419 行）**之後**。
兩者選擇器相同、權重相同 —— **分出勝負的只有出現順序**。

**決定：窄版那一組 media query 緊貼在基準規則之後**，不放進遠處的共用 `560px` 區塊。
程式裡留了註解說明原因，因為這個坑會在「把散落的 media query 收整」時被重新踩一次。

### Q-2. 相簿抽屜（這一章真正的修法）

**決定：鏡像文件牆已驗證的抽屜，不發明新模式。**

文件牆早就解過同一個問題（452 個資料夾、深 7～8 層），四個部件一一對應：

| 部件 | 文件牆 | 相片牆（本章新增） |
|---|---|---|
| 開關按鈕 | `.tree-toggle` / `#docTreeToggle` | `.album-toggle` / `#albumToggle` |
| 斷點同步 | `syncDocTreePane()` | `syncAlbumBar()` |
| 關閉 | `closeDocTree()` | `closeAlbumBar()` |
| 選取funnel | `selectDocFolder()` | `selectAlbum()`（**本章新抽**） |

**斷點一律 `max-width:900px`**，與文件牆同一個數字 —— 兩塊功能相似的導覽在不同寬度
變形，只會讓人以為介面壞了。

**不引入共用的斷點常數**（沿用「直接寫數字」的既有慣例）：CSS 自訂屬性**不能用在
`@media` 條件裡**，所謂的共用常數只能統一 JS 那半邊，換來的是兩塊本該一樣的程式
長得不一樣。這一點是刻意接受既有的重複。

#### 四個實作上的細節（每一個都有對應的坑）

1. **開關必須在 `#folderBar` 外面。** `paintFolderBar()` 是整批覆寫 `innerHTML`
   （三個呼叫點），放進去會被洗掉。位置對應 `#docTreeToggle` 放在 `.split` 之前。
2. **`syncAlbumBar()` 必須在 `await` 之前呼叫。** `loadFolders()` 的
   `catch { return; }` 會在 fetch 失敗時在畫任何東西之前 return —— 放在後面的話
   抽屜就停在未同步的狀態。`loadDocFolders()` 當初就是為此把同步放在最前面。
3. **`resize` 只在真的跨越斷點時動作**（`if (narrow === pWasNarrow) return;`），
   而且 gated 在 `!$('#photoView').hidden`。每次 resize 都同步的話，使用者在窄螢幕
   開著抽屜、手指稍微碰到縮放就被關掉。
4. **用自己的 `pWasNarrow`**，不共用文件牆的 `wasNarrow` —— 共用會讓「在文件牆
   縮放過」污染相片牆的下一次判斷。

#### 順手修掉的既有小 bug

原本點相簿標籤之後 `.fchip.on` 的高亮**要等下一次篩選或搜尋才更新**（內嵌的
onclick 只做了 `pstate.folder` ＋ `loadPhotos()`）。抽出 `selectAlbum()` 時補上
`paintFolderBar()`，順帶修掉。文件牆的 `selectDocFolder()` 本來就有做這件事
（在 `paintCrumbs()` 裡）。

### Q-3. 開關上的相簿名（這一章唯一比文件牆多做的事）

**這是必要功能，不是裝飾。**

文件牆收起抽屜之後還有麵包屑（`#docCrumbs` / `paintCrumbs()`）說「我在哪」。
**相片牆完全沒有等價物**：`#photoTitle` 是「相片 `<span id="photoCount">`」，
而程式只寫 `#photoCount`（張數）——**相簿名從來沒有出現在畫面上任何地方**。
`.fchip.on` 的高亮是唯一線索。

所以把 141 個標籤收起來的同時，如果不把名字放到開關上，等於**用一個更難察覺的
bug 換掉一個明顯的 bug**：使用者看得到瀑布流按鈕了，但不知道自己在看哪一本相簿。

> **附帶發現**：文件牆的 `#docTreeLabel` 是**死標記** —— 全 repo 只有 `index.html`
> 一處，沒有任何程式更新它，開關永遠寫著「選擇資料夾」。它靠麵包屑補足，所以沒有
> 人發現。這裡沒有現成實作可抄。

`paintAlbumToggle()` 三種狀態，順序就是優先序：

| # | 條件 | 顯示 | 為什麼 |
|---|---|---|---|
| 1 | `state.q` 有值 | `全庫搜尋中 · 選擇相簿` | 搜尋是跨全庫的，會蓋掉選中的相簿（`paintFolderBar()` 的 `sel = state.q ? null : …` 就是同一件事）。這時顯示相簿名等於**直接說謊** |
| 2 | 沒選相簿 | `所有相簿` | |
| 3 | 選了某一本 | `{相簿名} · {N} 張` | 用 `albumNames()` 的顯示名而不是原始路徑 —— 那個函式已處理過父子同名（`…/外拍/外拍`）的撞名，兩邊要一致 |

四個呼叫點，每一處都是那三種狀態可能變了的時刻：`syncAlbumBar()`（進相片牆／
跨斷點）、`selectAlbum()`（換相簿）、`paintFolderBar()` 結尾（`pfilter.items` 剛
載好，名字這時才算得出來）、以及頂部搜尋框的 handler（它本來就呼叫
`paintFolderBar()`，所以不需要額外接線）。

**不加 `aria-live`**：它會在每次 `paintFolderBar()`（含 200ms debounce 的篩選輸入）
都播報，噪音大於價值。使用者按下開關時焦點就在那顆按鈕上，報讀器會念出更新後的
按鈕名稱。

超長的名字（實測最長 71 字）用 `text-overflow:ellipsis` ＋ `white-space:nowrap`
＋ `min-width:0` 截斷，開關維持單行 42px。

### Q-4. 順手修的相關項

**Q-4a. `.pgrid.flow` 在 `≤420px` 從 1 欄改 2 欄。** 刪掉那條 media query，讓 2 欄
一路蓋到最窄。**單欄的瀑布流就是方格的慢速版**（原始比例、一張一張往下疊），等於
「按了按鈕但功能不存在」—— 跟本章的主題是同一件事的兩種表現。375px 下 2 欄約
178px/張，跟方格的 `minmax(160px)` 同量級。

**Q-4b. `.pgrid.flow` 的斷點 `700` → `720`。** 701～720px 這一段 `main` 已經換成
窄版 padding（斷點 720）卻還排 3 欄，兩個數字不一致造出一段 20px 的死區。
**只改真的互相矛盾的這一組** —— 1400/1000/900/820/560 各是不同東西的合理分界
（欄數階梯、PhotoSwipe 側欄轉底板、分頁器縮小），統一到一個值只會讓每個元件都在
錯的寬度變形。

**Q-4c. `.pgrid`（方格）補行動版欄寬。** `minmax(160px,1fr)` 一直沒有行動版覆寫，
375px 減 padding 只排得下 2 欄；而海報牆的 `.grid` 早在 720px 就降到
`minmax(120px)`。`≤560px` 改 `minmax(104px,1fr)`：375px 下是 3 欄，第一屏從 6 張
變 9 張。

**Q-4d. 修兩條過期註解**（見 Q-0）。

### Q-5. 不做什麼（刻意的邊界）

| 不做 | 為什麼 |
|---|---|
| **改 209px 的 sticky header** | 這是行動版第二大的問題（26% 視窗永久佔用），但它同時影響影片牆／文件牆／相片牆與 `.tree-pane{top:74px}`。正確修法是漢堡選單或底部導覽 —— 規模與回歸面遠大於本章。**另立 R 章追蹤** |
| **`.album-bar` 做 sticky** | 見 Q-1 |
| **相簿標籤改樹狀** | 141 本**全在同一層**（文件牆是 452 個、深 7～8 層）。樹狀對單層沒有幫助，還會丟掉封面縮圖 —— 相簿最好認的線索。抽屜保留縮圖 |
| **`#folderBar` 虛擬捲動** | 141 個節點（縮圖已有 `loading="lazy"`）在 `max-height:min(55vh,380px)` 的抽屜裡沒有效能問題。既有的 `#photoFolderQ` 已處理「太多找不到」 |
| **拿掉標記裡硬編的 `class="on"`** | `paintPhotoMode()` 在腳本尾端就跑，閃動只有一 frame；拿掉會讓無 JS 的情況變成兩顆都不亮，比現況差 |
| **為斷點引入共用常數** | 見 Q-2 |
| **讓 `init()` 呼叫 `showView()`** | 相片牆在按 nav 前完全不初始化是既有設計（省一次 API）。抽屜初始狀態由 `loadFolders()` → `syncAlbumBar()` 在按 nav 當下決定 —— **測試因此必須先 resize 再點 nav** |

### Q-6. 驗收

`tests/doctree_test.py` 的 `[13] 窄螢幕` 擴充（那一段本來就已經在 375px 下切到
相片牆，只是還沒斷言抽屜）。**擴充而不開新檔**：開新檔要重跑一次 fixture ＋ server
啟動（這一支最慢的部分），而且會讓「窄螢幕的兩塊導覽」的斷言散在兩個檔案 ——
下一個人改斷點時只會找到一半。

1. 窄螢幕出現 `#albumToggle`，`#folderBar` 預設收起
2. **`.pmode [data-pmode='flow']` 看得到**（使用者回報的原始症狀）
3. 沒選相簿時開關說「所有相簿」
4. 抽屜打得開，打開後仍不橫捲
5. 選完自動收起，開關顯示「相簿名 · N 張」
6. 超長相簿名有截斷、開關維持單行
7. 全庫搜尋時開關不再宣稱在某一本相簿
8. 瀑布流在 375px 是 2 欄、不橫捲
9. **窄轉寬時 `#folderBar` 自己回來、開關消失**（`hidden` 沒清掉的話桌機會整個消失）

`tests/pager_test.py` 兩處連帶修正：

- `TOP = CSS[index(".to-top{"):index(".pmode{")]` 的界標換成註解。`.pmode` 這個
  選擇器現在在 `@media` 區塊裡也會出現（靠右對齊），排在 `.to-top` 之前時
  `index()` 找到的是前面那個，**切出來是空字串，於是那兩個斷言永遠通過、測不到
  任何東西**。加了 `assert TOP.strip()` 防止下次再靜默失效。
- 「欄數隨寬度縮」原本數的是「有幾條 media query ≥ 4」—— 那是手段不是目的。
  Q-4a 拿掉一條之後條數變 3，而手機欄數其實是對的。改成把 max-width 階梯疊起來、
  直接算各寬度**真正生效**的欄數（1500→5、375→2、320→2、710 與 700 一致）。

> 這兩處都是同一類問題：**用「原始碼長什麼樣」代理「畫面是什麼行為」**。
> 換成算出實際生效值之後，斷言與 Playwright 量到的一致（375px → 2 欄）。
