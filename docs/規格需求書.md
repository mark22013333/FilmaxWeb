## 0. 修正紀錄：v1 的風險評估錯在哪

v1 把媒體庫移植 MSSQL 評為「中偏高風險」，這個判斷錯了兩次：

1. **用了假設的規模。**「1000 影片 + 5000 相片」是編的。真實規模是
   `media_file` 109、`photo` 679、`media_item` 15、`episode` 98、`play_state` 10。
2. **假設寫入形狀不變。** 用真實筆數重算，即使完全不改架構：

   | 寫入方式 | 往返 2ms | 往返 10ms | 往返 30ms |
   |---|---|---|---|
   | 現在的一句一交易（約 1,700～2,100 次） | 3～4 秒 | 17～21 秒 | 51～64 秒 |
   | 每 300～1,000 筆一批 | 約 8 次往返，任何延遲下都是「秒」等級 | | |

「40 秒到半小時」不成立。批次寫入就解決了，不是架構障礙。

### 三點質疑的回應

- **批次寫入** — 成立。但多執行緒該加在**讀相片**那段，不是資料庫。掃描的瓶頸是
  FTP 下載與 ffprobe；對資料庫加執行緒是在優化一個批次化後已不存在的瓶頸，
  還會把「單一寫入者、無競態」推進「要處理死鎖重試」。
- **不用外鍵** — 成立。代價只有一個且可量化：要有「孤兒數量」指標當體溫計。
- **時間欄位可設計解決** — 成立，而且比預期更該修：**問題現在就在資料上發生**（見 G-2）。

### 時間欄位的裁決

兩個 agent 給了相反建議（epoch 整數 vs `DATETIME2`）。採用 **Python 端一律 epoch、
SQLite 存整數、MSSQL 存 `DATETIME2`** — 沿用 `users_mssql.py` 已在運行且有測試的做法。
決定性理由：`filmax_users` 與 `filmax_audit` 已用 `DATETIME2`，媒體庫改存 epoch 會讓
同一個資料庫有兩種時間慣例。

## A. 儲存後端與資料層

**預設 SQLite，MSSQL 為選配。** 這一節多數工作與用哪個資料庫無關。

### A-1 設定開關

```ini
USER_STORE=mssql      # 帳號
MEDIA_STORE=sqlite    # 媒體庫，預設值
```

- 兩個開關獨立；值只接受 `sqlite` / `mssql`，寫錯就啟動報錯。
- 設 `mssql` 但連線資訊不齊 → 報錯指出缺哪一項，**不自動退回 SQLite**。
- 沒設 `USER_STORE` 但有 `MSSQL_HOST` → 沿用現有行為並在日誌提醒。

### A-2 批次寫入

```python
with store.batch() as b:
    b.upsert_file({...})     # 只進緩衝
    # 累積到 N 筆自動寫出並 commit；離開 with 強制寫出
```

**不是每張表都適合批次：**

| 表 | 批次 | 原因 |
|---|---|---|
| `media_file` / `photo` | 可以 | 純 upsert，不需當場拿 id |
| `media_item` / `episode` | **不批次** | 寫檔案列前必須先有 `item_id`。改用行程內註冊表：掃描開始時把 15 筆 `(guess_key → id)` 載進記憶體，解析時持鎖序列化 |

只有 15 個條目，序列化成本是零；硬做成批次只會製造難修的競態
（兩執行緒同時建同一個 `guess_key` → 同一部影集出現兩張海報，一張 12 集一張 1 集）。

**若日後啟用 MSSQL，批次有三個必要條件：**

1. `fast_executemany` 必須搭配 `setinputsizes()`（用 schema 寬度，不讓 pyodbc 猜）。
   這是正確性不是優化 — 已知會截斷，更糟的是**前一列的字串殘留覆蓋下一列，無錯誤訊息**。
2. **寫完要對帳。** `fast_executemany` 遇到違反約束的列**不拋例外**，有效列照樣寫入、
   失敗列靜默消失。必須 `SELECT COUNT(*)` 核對，不符就整批退回。
3. `executemany` 不能取回結果集，拿不到 `OUTPUT INSERTED.id`。

`app/mssql.py` 目前 `autocommit=True` 寫死、沒有 `tx()`/`commit`/`rollback`/`executemany`，
而它的模組說明宣稱有 `executemany`。**這是我寫的，一併修。**

### A-3 時間欄位

| 類別 | 欄位 | Python | SQLite | MSSQL |
|---|---|---|---|---|
| 時間點 | `added_at` `updated_at` `seen_at` `mtime` `taken_at` | epoch 整數秒 | `INTEGER` | `DATETIME2(0)` |
| 日期 | `episode.air_date` | 字串 | `TEXT` | `DATE` |
| **時間長度** | `duration` `position` | **維持浮點，一個字都不要動** | | |

> **時間點與時間長度這條界線畫錯就是使用者立刻有感的災難。**
> `play_state.position` 若取整成秒，續播每次最多漂 1 秒，`WHERE position > 30`
> 這種門檻的行為也會變。使用者的抱怨會是「每次繼續看都往前跳」。

**三個配套：**

1. **具體化排序鍵 `sort_ts`** — 寫入時算好 `COALESCE(taken_at, mtime, added_at)`，
   `NOT NULL` 加索引。同時解掉排序錯誤與「`COALESCE` 用不到索引」。
   代價：衍生資料只能在 `upsert_photo()` 一處被寫，要有測試釘住。
2. **保留 `taken_at_raw`** — EXIF 原始字串一字不改。EXIF 的 `DateTimeOriginal` 沒有時區，
   轉 epoch 必須假設一個，而那假設在出國拍、相機沒調時鐘的照片上一定是錯的。
   另加 `taken_tz` 記錄這個 epoch 是 EXIF 給的還是我們假設的。
3. **值域 CHECK 約束** — `CHECK (taken_at IS NULL OR taken_at BETWEEN 0 AND 4102444800)`。
   `DATETIME2` 天生擋得住亂值，整數欄位擋不住：把毫秒當秒傳會安靜存進去，
   然後那筆永遠排最前面。兩個後端都要加。

### A-4 不用外鍵，改用單一刪除進入點

```python
store.purge(item_ids=..., file_ids=..., photo_ids=..., reason='scan_vanished')
store.sweep(mode='report' | 'fix')
```

`purge()` 是唯一的刪除進入點，所有連帶關係（含磁碟上的縮圖檔）都在裡面展開，
`reason` 必填並進稽核。

**清掃時機與寬限期：**

| 時機 | 模式 | 理由 |
|---|---|---|
| 掃描的 `finally` | `fix` | 「被取消」與「出錯」正是孤兒最多的結局，只掛成功路徑等於永遠不清最需要清的那次 |
| 服務啟動 | `report` | **刻意不修**。啟動路徑自動刪資料很糟，尤其剛還原備份或剛換後端之後 |
| 後台按鈕 | 兩種 | 先 dry-run 看清單 |

第 5、6、7 類孤兒必須有 1 小時寬限期 — 索引流程是「先建條目、再寫檔案列」，
兩步之間條目就是合法的孤兒。

**孤兒數量要露在 `/api/stats` 與後台總覽。** 沒有外鍵的資料庫，孤兒計數就是體溫計。

### A-5 MSSQL 媒體庫（選配，第四期）

A-2～A-4 做完後只是多實作一個檔案。額外工作：Flyway `V6` 建表、`guess_key` 用篩選唯一索引、
分頁改 `OFFSET/FETCH`、子查詢 `LIMIT 1` 改 `CROSS APPLY`、`lastrowid` 改 `OUTPUT INSERTED.id`。

**upsert 不要用 `MERGE`** — SQL Server 社群的權威意見是它有從未修復的缺陷。
改用暫存表 + 集合式 `UPDATE...FROM JOIN` 加 `INSERT...WHERE NOT EXISTS`，
帶 `WITH (UPDLOCK, SERIALIZABLE)`。附帶好處：`WHERE` 加變更偵測後，
重複掃描時沒變的檔案完全不產生寫入。

## B. 管理後台

獨立的 `/admin`，管理者專用，手機可用。

### 分區

| 分區 | 最少要有 |
|---|---|
| **總覽** | 版本與執行時間、影片／相片／容量計數、**磁碟剩餘空間**、最近 10 筆活動、執行中的掃描、待審核人數、**孤兒計數**、問題警示 |
| **媒體庫** | 掃描控制、**完整進度（含目前看不到的相片階段）**、未刮削清單、失敗檔案與錯誤、FTP 目錄瀏覽器 |
| **使用者** | 清單與狀態篩選、核准／拒絕／停權／改角色／**刪除**、**備註欄位**、最後登入來源 |
| **播放與轉碼** | ffmpeg 狀態、硬體加速探測、編碼器深度診斷、轉碼實測、**FTP 併發量測**、GPU、清快取 |
| **系統** | **資料庫狀態**、FTP 測試、TMDB 狀態、**系統參數設定（見 B+）** |
| **紀錄** | **登入稽核（伺服器端分頁）**、掃描日誌、設定變更稽核 |

### 刻意不做

Live TV／DVR、DLNA、外掛系統、自訂角色矩陣、標籤式權限、每人頻寬配額、
家長時段表、CPU/RAM 歷史圖表、Top Users 排行、多伺服器切換、通知渠道大全。

角色維持兩種（管理員／唯讀）。

### 手機版

- 斷點 768px。以上固定側欄，以下漢堡鍵 + 抽屜。
- 抽屜點連結自動關閉；**iOS 不做邊緣滑動開啟**（會跟系統返回手勢打架）。
- 表格換成卡片，**不是**用 CSS 藏欄位（藏起來等於資料消失且無替代入口）。
- 手機保留：看最近錯誤、觸發掃描、停用使用者、看登入紀錄。
- 手機隱藏：清空媒體庫、批次操作、ffmpeg 參數這類寬表單。
- 觸控目標 ≥44×44px；寬內容包在自己的 `overflow-x:auto`，body 永不橫捲。

### 安全與工程

- `/admin` 路由要**自己檢查 `auth.is_admin`** — 中介層只驗登入不驗角色。
- `admin.js` 在 `/static/`，**不需登入就能下載**，不能寫死任何敏感資訊。
- 危險操作二次確認，文案**重述對象名稱**。
- 登入稽核伺服器端分頁，預設 25 筆／頁。
- 每張表要有空狀態與錯誤態。
- 沿用既有 CSS 變數與元件類別（`.file-row` `.pill` `.st` `.chip`）。

## B+. 系統參數設定

同時支援 `.env` 與資料庫。研究了 Immich、Grafana、Gitea、Sonarr、Navidrome、
Nextcloud、Home Assistant 七套的實際做法。

### 核心原則：不要讓兩邊比大小

| 方向 | 最惡毒的失效模式 | 實際案例 |
|---|---|---|
| **env 贏** | **存了但沒生效** — 在後台改值、按存檔、看到成功提示、行為完全沒變，也沒有警告 | Sonarr／Radarr 的原始碼就是這個行為 |
| **DB 贏** | **改 .env 沒反應** — `.env` 是自架使用者唯一熟悉的介面，變成裝飾品之後使用者會認定程式壞了。輪替金鑰時只改 `.env` 以為換好了、實際仍用舊值，是安全事故等級 | Gitea 有一個 issue 正是如此 |

**選 env 贏，但要付 env 贏的稅。** DB 贏的失效模式是安全與復原性硬傷；
env 贏的是純 UX 問題，**而 UX 問題可以用 UI 解決**。
解法不是比大小，是**把「誰在管這一項」變成畫面上看得見的東西**。

### 設定分層（四個機械化問句）

| 問句 | 答「是」 | 例 |
|---|---|---|
| 改錯了會不會讓我連後台都進不去？（或讀它時資料庫還沒連上） | **Tier 0** 只能放 .env | MSSQL 連線、`HOST`/`PORT`、`AUTH_SECRET`、資料目錄、`USER_STORE`/`MEDIA_STORE` |
| 這個值會被當命令、路徑或程式碼執行嗎？（或改它會擴大信任邊界） | **Tier 4** 不放 UI | `FFMPEG_PATH`、`LIBRARY_ROOTS`、`TRUST_PROXY`、`LOCAL_NETWORKS` |
| 洩漏了是外部系統倒楣嗎？ | **Tier 1** 秘密 | `TMDB_API_KEY`、`FTP_PASSWORD`、`GOOGLE_CLIENT_SECRET` |
| 啟動時被拿去建立長生命週期的東西了嗎？ | **Tier 3** 需重啟／重載 | 連線池大小、探測併發數、快取上限 |
| 以上都不是 | **Tier 2** DB + UI，即時生效 | 掃描排除、轉碼參數、遠端畫質、相片門檻、TMDB 語言、字幕預設 |

Tier 2 剛好都是改了立刻生效的 — 這不是巧合，Gitea 遷移設定到後台用的判準就是這條。

> Tier 4 的先例：Navidrome 把轉碼設定 UI 預設關閉，理由寫在安全文件裡 ——
> 「它讓攻擊者可以在你的伺服器上執行任意命令」。`FFMPEG_PATH` 是同一類東西。

### 解析順序與 API

```
.env / 環境變數  >  資料庫  >  程式內建預設值
```

一條規則，全部一致，沒有例外清單。API 不能只回生效值：

```json
{
  "key": "TRANSCODE_CRF",
  "effective": { "value": 21, "source": "env" },
  "candidates": { "env": 21, "db": 23, "default": 21 },
  "locked": true, "shadowed": true,
  "applyMode": "hot", "secret": false
}
```

`shadowed` 一個欄位就解決「.env 改了但 DB 已經有值」的全部歧義。

### UI 規則

- **逐欄位標示鎖定，不是整頁鎖。** Immich 是「有設定檔就整個後台唯讀」，
  50 幾項橫跨四個 tier 全鎖等於後台白做。
- 被鎖：輸入框停用 + 鎖頭 + 「此項由環境變數 `X` 設定，無法在此修改」。
- 被鎖且 shadowed：多一行警示 + `[清除後台儲存值]` 按鈕。
- **絕不能讓停用的欄位送出後才在後端報錯。** Immich 目前就有這個 bug。
- 逐欄位「已修改未儲存」標記 + 「重設為預設值」「重設為上次儲存值」。
- **DB 只存與預設值不同的項目**（相等就刪列）。

### 三態生效方式

| applyMode | 實作要求 | UI |
|---|---|---|
| `hot` | 讀取一律走 `settings.get(key)`，**禁止模組頂層解構成常數** | 「已生效」 |
| `reload` | 先驗證，失敗整批不寫入；成功才寫入並重建子系統 | 「已套用」 |
| `restart` | 只寫入，不套用 | 常駐「需重啟」標記 |

> **最容易悄悄漂移的一項。** 有人在模組頂層寫 `CRF = settings.crf`，那項就從 `hot`
> 退化成 `restart`，**而 UI 仍顯示「已生效」**。要在測試裡釘住。
> 「需重啟」橫幅要能自己消失（比對行程啟動時間與最後變更時間）。

### 秘密

- **唯寫欄位。** API 一律回遮罩 + 「是否已設定」+ 「最後更新時間」，任何情況都不回明文。
- 存 DB 時加密，密文加固定前綴。加密金鑰本身是 Tier 0。
- 支援 `XXX_FILE` 後綴從檔案讀。
- 日誌過濾掛成 logger hook，不在每個呼叫點各自處理。
- **敏感不等於密碼**：MSSQL 主機名、FTP 主機名、媒體目錄絕對路徑都要標敏感，那是內網拓撲情報。
- 秘密進 DB 等於「DB 備份 = 秘密備份」，備份加密要一起決定。

### 其他必要機制

- **啟動時漂移掃描** → 後台橫幅「有 N 項被環境變數覆蓋」。**絕不自動刪 DB 的值。**
- **env 打錯字要抓出來** — `TMDB_API_KAY=xxx` 現在是完全靜默失效的。
- **驗證嚴格度**：`.env` 無效 → 啟動失敗；DB 值無效 → 退回預設並在後台顯示錯誤。
- **CLI 復原路徑** `python -m app.config diff/get/set/unset/list`（後台進不去時唯一救援）。
- **設定變更稽核**：誰、何時、哪一項、從什麼改成什麼。秘密只記「已變更」與時間，
  連遮罩後的值都不記（長度也是情報）。研究的七套**沒有一套**做這件事。
- **別讓後台把自己鎖死**：改綁定位址／對外網址／驗證方式前要二次確認並顯示 CLI 復原指令。

## C. 影集分組

`/媒體資料庫/HBO/來！金來號 ！/01/來！金來號 ！01.mp4` 這種結構，
五集變成**五個獨立的「電影」條目**。

**原因與 TMDB 無關**：檔名結尾的 `01` 沒被認出是集數（緊貼標題、沒有 `EP`／`第01集`／`S01E01` 標記），
上層資料夾 `01` 也沒被認出是季別。集數留在標題裡 → 每集算出不同的合併鍵。
是**先被拆開才導致 TMDB 查不到**，不是反過來。

### 新增規則

| # | 規則 | 條件 |
|---|---|---|
| 1 | 所在資料夾是純數字或 `EP01`／`E01`／`第01集` → 那是集數，劇名取上一層 | 需 **≥2 個同型態兄弟資料夾** |
| 2 | 檔名尾端 1–3 位數字當集數 | 需**同群組內多個檔案共用相同標題前綴、尾數不同**。單檔不套用 |
| 3 | 規則 1 或 2 成立 → `kind` 強制為 `tv` | |

**結構性調整**：`parse()` 現在逐檔判斷，不知道兄弟檔案與兄弟資料夾長什麼樣。
規則 1、2 都需要群組資訊，所以 `walk()` 要把同層的兄弟名稱一起傳進解析器。

### 重新分組

> **目前的完整掃描不會重新解析檔名。** `_index_file` 開頭就是
> 「檔案大小沒變就只更新 `seen_at` 然後 return」。

- 新增 `POST /api/scan?full=true&reparse=true` 強制重新解析。
- 後台放「重新分組」按鈕，說明「會重新解析所有檔名，不會重新下載中繼資料」。
- 重新分組後清孤兒條目。

## F. iPhone 全螢幕

`pl.requestFullscreen?.()` 中 `pl` 是 `<div>`，而 **iOS Safari 上 `div.requestFullscreen` 不存在**，
`?.` 讓它安靜地什麼都不做。也沒有 `webkitRequestFullscreen` 備援。

### 三種模式

| 模式 | 做法 | 保留 | 失去 |
|---|---|---|---|
| **自動**（預設） | 桌機／Android 用 Fullscreen API；iPhone 用網頁全螢幕 | 各平台最好的結果 | — |
| **網頁全螢幕** | CSS `position:fixed` 撐滿、`100dvh`、鎖背景捲動 | **自訂控制列、自繪字幕全保留** | Safari 網址列可能還在 |
| **原生全螢幕** | `video.webkitEnterFullscreen()` | 畫面乾淨、系統手勢 | 自訂控制列與**自繪字幕的外觀設定** |

### 原生全螢幕下的字幕

不必在「原生全螢幕」與「有字幕」之間二選一。已解析好的 cue 可以同時餵給原生字幕軌：

```js
const t = video.addTextTrack('subtitles', label, lang);
t.mode = 'disabled';                        // 平常關著，自繪那層在工作
t.addCue(new VTTCue(start, end, text));     // 邊解析邊加，沿用現有漸進式載入
```

進入原生全螢幕時切成 `showing` 並隱藏自繪圖層，退出時反過來。
**漸進式字幕載入（大檔第一句 0.11 秒）的優勢完全保留。**

### 其他

- 補 `webkitRequestFullscreen` 備援。
- 監聽 `webkitendfullscreen`，使用者從系統播放器退出時還原狀態。
- 版面高度改 `100dvh`。
- 橫向鎖定：能用的平台才呼叫；**iOS Safari 不支援，不要假裝有**，也不要因它失敗就中止全螢幕。

**需要在實體 iPhone 上實測** — 開發環境沒有 iOS，模擬器重現不了 `webkitEnterFullscreen` 的真實行為。

## G. 現在就已經壞掉的東西

盤點資料層時挖出的既有缺陷，每一個都在資料或程式碼上驗證過。

### G-1 孤兒條目清理只有在「有相片」時才會跑　【高】

```python
if seen_photos and not _cancel.is_set():
    with db.tx() as conn:
        ...刪掉消失的相片...
        conn.execute("DELETE FROM media_item WHERE id NOT IN (...)")   # ← 在這裡面
```

影片與相片是兩件獨立的事卻被綁在一起。**純影片的片庫永遠不會清孤兒條目**；
相片掃描被取消或出錯時也不會清。

### G-2 相片排序是錯的　【高】

`photo.mtime` 存 `2026-07-12T14:30:29`（**T** 分隔），
`photo.taken_at` 存 `2026-03-19 00:29:05`（**空格**分隔），
而排序是 `ORDER BY COALESCE(taken_at, mtime) DESC` — 字串比大小。

`' '`(0x20) < `'T'`(0x54)，第 11 個字元就分勝負，**後面的時間根本沒被比到**：

```
taken_at = '2026-03-19 23:59:59'   ← 晚上快 12 點
mtime    = '2026-03-19T00:00:01'   ← 凌晨 12 點過 1 秒
字串比較：mtime 比較「大」，排在前面
```

**同一天內，只有 mtime 的照片永遠排在有 EXIF 的前面**，不管實際差多久。
資料庫裡排最前面的 8 張全是 mtime 那組。FTP 的 mtime 還有三種其他格式
（`Mar 15 10:22`、`03-15-24 10:22AM`、空字串），`Mar` 開頭的會直接跳到全表最上面。

修法見 A-3。

### G-3 按下「停止掃描」最多還要等 90 秒 × 併發數　【中】

探測函式只在**進入時**檢查一次取消旗標，而 `ffprobe` 的 timeout 是 90 秒。
使用者看到的是「按了沒反應」。修法：旗標傳進去、每個可中斷點檢查、子行程能被終止。

### G-4 98 集的影集會有 98 個工作搶著產生同一張底圖　【中】

`COALESCE` 讓它不會覆蓋既有值，但**兩個工作同時看到「還沒有底圖」時，兩邊都會各跑一次 ffmpeg 截圖**
— 兩次轉碼、兩個磁碟檔，其中一個立刻變成孤兒。
修法：探測階段只記錄候選，全部結束後單執行緒處理一次。

### G-5 縮圖檔名重用可能讓你看到別人的照片　【高】

縮圖檔名是 `ph_{id}.jpg`，而產生函式**看到同名檔已存在就直接回傳，不重畫**。
id **會**被重用：還原備份、切換後端、砍掉 `library.db` 重掃之後，
新的第 7 張仍叫 `ph_7.jpg`，於是顯示**舊的第 7 張**的縮圖。點進去是對的，牆上是錯的。

**這是隱私問題，不是顯示問題。** 決策 4 已確認採徹底修法：檔名改用**內容雜湊**。
既有 679 張縮圖要重新產生一次。

### 其他較小的

| 問題 | 影響 | 嚴重度 |
|---|---|---|
| CSP 擋掉 `image.tmdb.org`，但手動配對縮圖指向那裡 | 該功能縮圖全是破圖 | 中 |
| 掃描面板的階段對照表沒有 `photos` key | 679 張相片的掃描全程不可見，進度條直接跳 100% | 中 |
| `/api/scan/status` 沒有權限保護，回傳含掃描日誌 | 唯讀使用者看得到 FTP 路徑結構 | 中 |
| `photos_found` 名不符實（沒變動的走早退路徑不計入） | 那數字其實是「新增或變更數」 | 低 |
| `mssql.py` 說明宣稱有 `executemany`（不存在）、`autocommit=True` 寫死 | 批次寫入在 MSSQL 側無法原子化 | 中 |

### 決策 2 的補充

`FTP_HOST` 是 `127.0.0.1`，FTP 與服務跑在同一台機器，開發環境連不到，
也沒有能在該機器執行指令的工具。因此改為交付量測工具。

**v1 的測速是錯的，已修正。** 第一次交付的版本在使用者的伺服器上量到
「每條連線都剛好 0.75 MB/s、併發完美線性」。回頭比對發現開發環境的 loopback
測試也是同一個數字 —— 兩台完全不同的伺服器不可能一致，那是工具本身的產物。

原因：測速迴圈抓滿 3MB 後呼叫 `ftplib.abort()` 中止傳輸，而 **`abort()` 會讓
控制連線失去同步** —— 下一個指令會讀到上一個指令殘留的回應（實測：PASV 讀到
`200 Type set to: Binary`），整條連線從此壞掉。所以每條連線只成功跑完**一輪**，
剩下的時間全在空轉。而「3 MB ÷ 4 秒時間窗」＝ 0.75 MB/s，
在任何伺服器上都會量到同一個數字，看起來像真的資料。

修正：改用 `ntransfercmd()` 拿原始 socket，讀夠就直接關掉資料連線
（伺服器回 426，預期中），控制連線保持乾淨。實測對照：

| 做法 | 4 秒內完成輪數 | 量到的速度 | 控制連線 |
|---|---|---|---|
| v1：`retrbinary` + `abort()` | 1 | 假數字 | **壞掉** |
| 整檔下載不中斷 | — | 1763 MB/s（真正天花板） | 正常 |
| v2：`ntransfercmd` + 提前關閉 | 305 | 229 MB/s | 正常 |

同時加上**輪數回報**：某一級如果只跑完一兩輪，那個 MB/s 就是「一輪除以時間窗」
而不是頻寬，會標示為不可信並排除在推算之外。這種錯不該再靠人眼發現。

**記憶體約束也修了。** 原本用 `MAX_PHOTO_MB`（80MB）估每條連線的佔用，
但那是「超過就不讀」的門檻，不是實際佔用量。改用資料庫裡的真實最大值 ——
實際最大的一張是 30.9MB（p95 19.3MB、中位數 2.02MB），保守程度差了 2.6 倍。
還沒掃過相片時才退回用門檻估，並註明「掃過之後再跑一次會更準」。

**連線數上限的部分準確度已驗證** — 架了兩台上限已知的 FTP 伺服器測試：

| 伺服器設定 | 工具量到 | 結果 |
|---|---|---|
| `max_cons = 7` | 6 條成功，第 7 條被拒 | 正確 |
| `max_cons = 15` | 14 條成功，第 15 條被拒 | 正確 |

執行方式：`測試FTP併發.bat`。只做登入、列目錄、下載一小段測速，不寫入任何東西。
這支工具之後會變成後台「播放與轉碼」分區的一顆按鈕。

### 量測結果推翻了「多執行緒該加在讀相片」這個前提

修好之後在使用者的伺服器上實測：**單條 295 MB/s、3 條 1045 MB/s，
679 張共 2.7GB 只要約 10 秒讀完**。FTP 完全不是瓶頸。

於是進一步量相片階段的時間到底花在哪（用符合真實大小分布的圖片跑 `app/photo.py`）：

| 階段 | 679 張的成本 | 佔比 |
|---|---|---|
| FTP 讀取 | ~10 秒 | 6% |
| 讀 EXIF 與尺寸 | 0.5 秒 | 0.3% |
| **產生縮圖** | **~149 秒** | **94%** |

`read_info` 幾乎免費 —— PIL 的 `Image.open` 是惰性的，只讀檔頭。
**所有成本都在 `make_thumb` 的完整解碼。**

**因此第二期的做法要改，而且有一個比多執行緒更好的解法：**

1. **`im.draft("RGB", (480, 480))`** —— 讓 JPEG 解碼器直接以 1/2、1/4、1/8 尺寸解碼，
   不必先把整張全解出來再縮小。實測 **219.6 ms → 86.2 ms，快 2.5 倍**
   （679 張：149 秒 → 59 秒）。畫質差異平均像素差 1.84/255，視覺上看不出來。
   **一行程式碼，不增加記憶體，沒有執行緒的複雜度。優先做這個。**
2. 多執行緒再疊上去。PIL 的解碼會釋放 GIL，實測 2 核心上約 1.8～2.0 倍。
3. 兩個都做：149 秒 → 約 25～30 秒。

**`PHOTO_CONCURRENCY` 的預設值要照 CPU 核心數算，不是照 FTP 上限算。**
量測工具已更新：頻寬轉折點只作為資訊回報，不列入限制條件 ——
拿一個「跑滿頻寬時」的門檻去限制一個「只佔 6% 時間」的工作是錯的。
